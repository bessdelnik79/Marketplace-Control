# Сверка реальных отчётов WB API для P0.3

Проверка: 2026-09-23, один подключённый магазин на тестовой VM. Источники — текущие ответы WB `POST /api/finance/v1/sales-reports/list` и `POST /api/finance/v1/sales-reports/detailed`, а также принятые версии этих отчётов в БД. Первичная API-сверка выполнена без печатной формы; отдельная тестовая сверка формы описана ниже. Идентификаторы магазина, отчётов, строки, суммы, токен и исходные выгрузки не сохраняются в Git.

## Покрытие и контрольные суммы

- Период отчётов: 2026-06-15 — 2026-09-20. В списке WB — 20 еженедельных отчётов; в актуальной детализации — 992 строки, из них 980 строк `reportType=1` и 12 строк `reportType=2`. Следующий запрос с последним `rrdId` вернул `204`, то есть проверена граница выгрузки.
- Для каждого из 20 отчётов по идентификатору сверены `retailAmountSum`, `forPaySum`, `deliveryServiceSum`, `paidStorageSum`, `paidAcceptanceSum`, `deductionSum`, `penaltySum`, `additionalPaymentSum`, `cashbackAmountSum`, `cashbackDiscountSum`, `cashbackCommissionChangeSum`: 220 из 220 сравнений без расхождений. `retailAmount` и `forPay` суммировались как продажи минус возвраты; остальные перечисленные поля — по исходному знаку. Это подтверждение на данном наборе, не универсальное доказательство смысла всех ненулевых полей.
- `bankPaymentSum` присутствует только в сводном ответе и пока не сохраняется рабочим импортом. До отдельной проверки формула итога к оплате оставалась неподтверждённой.
- Дополнительная read-only сверка: сумма `forPay` по продажам минус возвраты, затем минус исходные `deliveryService`, `paidStorage`, `paidAcceptance`, `deduction`, `penalty`, `additionalPayment` совпала с `bankPaymentSum` на всех 20 текущих отчётах. Ненулевое покрытие: приёмка — 6 отчётов, хранение — 15, удержания — 7, штраф — 1, корректировка вознаграждения — 3. `cashbackAmountSum` и `cashbackCommissionChangeSum` были нулевыми во всех отчётах; `cashbackDiscountSum` был ненулевым в одном и уже не требовал отдельного прибавления. Поэтому это доказанная для образца сверка, но ещё не универсальное правило и не активный production-контроль.
- Добровольно предоставленная печатная форма за 2026-07-13 — 2026-07-19 сопоставлена с тем же магазином, ID, типом, валютой и периодом отчёта. Совпали стоимость реализованного товара, итог к перечислению, эквайринг, возмещение перевозки и ПВЗ. Общий итог вознаграждения совпал с формулой ответа поддержки при округлении `vw` по строкам до копеек; отдельные печатные строки вознаграждения без НДС и НДС напрямую из `vw`/`vwNds` не доказаны. Форма использована только для теста, не хранится в продукте и не является входом расчёта.
- Сохранённые версии трёх отчётов устарели относительно текущего API: 2026-06-15 — 2026-06-21 (69 строк вместо 81), 2026-08-10 — 2026-08-16 (9 вместо 60), 2026-08-17 — 2026-08-23 (76 вместо 89). По свежей детализации их сводные суммы сходятся. Текущее повторное окно импорта 35 дней не обнаруживает все такие изменения.

Повторная проверка на VM: три изменённых отчёта теперь являются текущими — 81, 60 и 89 строк соответственно. За 2026-08-17 — 2026-08-23 WB возвращает ещё один отдельный неизменившийся отчёт на 2 строки. Для июньского отчёта создана новая версия; в августовских отчётах API вновь отдал содержимое ранее сохранённых принятых версий, поэтому исправленный импорт повторно выбрал эти версии без дублирования строк. Сверка 11 сводных полей для каждого из четырёх отчётов прошла; отдельно подтверждены 33 сравнения при повторном августовском прогоне. Результат расчёта остался `partial`. Автоматическое обнаружение изменений за пределами 35-дневного окна ещё не реализовано.

Последние 32 строки имеют ненулевые `ppvzReward` либо `cashbackDiscount`. Слово «возврат» в названии первой операции не делает её возвратом продажи. Для точных магазинных строк ПВЗ правило источника подтверждено отдельно ниже; компенсация лояльности и любые несовпадающие сочетания по-прежнему остаются fail-closed.

Дополнительная проверка 31 строки ПВЗ показала близость суммы исходных полей `ppvzReward + vw + vwNds` к нулю, но это только наблюдение выборки и не правило расчёта. В `wb-finance-v7` поля не связываются и не взаимозачитываются: каждый присутствующий компонент классифицируется независимо. `ppvzReward` всегда записывается как расход `-abs(value)` независимо от исходного знака; `vw` и `vwNds` являются знаковыми расходами, поэтому исходный плюс становится расходом, а минус — сторно. Все четыре подтверждённых поля `vw`, `vwNds`, `rebillLogisticCost` и `ppvzReward` округляются до копеек по каждой строке. Служебные `srid`/`shkId` не создают товарную привязку. Несовпадающая операция без товарной связи остаётся fail-closed; компенсация лояльности проверяется отдельно.

Контрольная неделя 07–13.09.2026 по отчётам №842116510 и №846123493 даёт 4 669,61 ₽ расходов WB до себестоимости: `vw` 1 870,74 ₽, `vwNds` 411,55 ₽, `rebillLogisticCost` 100,24 ₽, логистика 1 403,00 ₽, приёмка 70,00 ₽, хранение 5,51 ₽, эквайринг 301,19 ₽, `ppvzReward` 203,38 ₽ и удержание продвижения 304,00 ₽. Это та же итоговая сумма, что и прежняя сверка со свёрнутыми строками вознаграждения; `rebillLogisticCost` не прибавляется поверх обоих представлений одновременно.

Предоставленный селлером перечень строк печатной формы уточняет контроль: выдача и возврат на ПВЗ — подпункт общего зачёта (2.7 на новом скриншоте, 2.8 в форме за июль), компенсация скидки лояльности — 1.5, итог к перечислению — 8. Нумерацию подпунктов 2.x нельзя считать стабильным идентификатором. Поэтому нулевую сумму трёх API-полей на специальных строках нельзя подменять нулём печатной строки ПВЗ. В июльской форме внутренние равенства 1, 2 и 8 сошлись; новый скриншот не содержит сумм, а соответствие всех строк API ещё не доказано. [Формулы и границы сверки](financial-formulas.md#контрольная-арифметика-печатной-формы-расчёты-с-продавцом).

## Что остаётся до закрытия критерия P0.3

Обновление: при очередной синхронизации уже выполняется ротационная глубокая проверка одной старой недели по исходным строкам. Пункт 1 ниже описывает прежнее состояние: самостоятельный фоновый запуск без визита селлера остаётся в P0.6, а актуальность всего архива будет подтверждена только после полного оборота недель.

1. Добавить автоматическое сравнение ранее принятых отчётов за пределами 35-дневного окна со списком WB; три обнаружленных изменения уже точечно загружены и сверены. При повторном появлении ранее принятого checksum возвращать его в текущую версию без создания дубля.
2. Продолжить проверку иных неклассифицированных типов операций. Для ПВЗ не переносить source-классификацию точной магазинной строки на другие названия операций или строки с реальным товарным идентификатором.
3. Довести наблюдаемую формулу `bankPaymentSum` до версированного контроля: проверить отсутствующие ненулевые случаи cashback-полей, оба знака корректировок, хранить сводный ответ по ID отчёта и покрыть расхождения тестами. Совпадение нулевых сумм само по себе не подтверждает правило.

Документация WB: [методы списка и детализации отчётов реализации](https://dev.wildberries.ru/docs/openapi/financial-reports-and-accounting).
