# AI-оркестратор Marketplace Control

AI-оркестратор — это основная задача Codex, открытая в репозитории Marketplace Control. Она отвечает за весь цикл работы: понимает запрос, исследует код, делит независимые части между субагентами, интегрирует изменения, организует ревью и проверки, после чего создаёт один коммит и отправляет его в `origin/main`.

Оркестратор работает только внутри запущенной задачи. Он не продолжает разработку по расписанию, не выбирает следующий пункт MVP без запроса пользователя и не расширяет продуктовый scope самостоятельно. Новые правила гарантированно загружаются при открытии следующей задачи Codex.

Проект использует штатные механизмы Codex: инструкции в `AGENTS.md`, настройки в `.codex/config.toml` и профили в `.codex/agents/`. Основание формата — [официальная документация OpenAI по субагентам](https://developers.openai.com/es-419/docs/agent-configuration/subagents).

## Когда включается оркестрация

Оркестратор делегирует работу, когда задача затрагивает несколько подсистем, требует отдельного исследования, содержит независимые части или связана с повышенным риском: БД, аутентификацией, финансовыми расчётами, внешними API и безопасностью.

Простые локальные изменения выполняются основной задачей без исследователя и исполнителей, если такое делегирование не даст практической пользы. Независимый `mc_reviewer` перед коммитом остаётся обязательным. Это уменьшает задержку и расход токенов, не отменяя контроль итогового diff.

## Роли

| Профиль | Доступ | Назначение |
|---|---|---|
| `mc_explorer` | Только чтение | Находит точки входа, зависимости, тесты, риски и безопасные границы рабочих частей. |
| `mc_implementer` | Запись в workspace | Реализует одну ограниченную часть только в явно назначенных файлах. Можно запустить до двух исполнителей параллельно. |
| `mc_reviewer` | Только чтение | Независимо проверяет итоговый diff на ошибки, регрессии, безопасность и пробелы в тестах. |

Модель и уровень reasoning в профилях не закреплены: субагенты наследуют настройки основной задачи.

## Рабочий процесс

1. Основная задача читает запрос, применимые инструкции и документацию, проверяет `git status` и связанные участки кода.
2. Для нетривиальной задачи `mc_explorer` уточняет архитектуру и предлагает независимые рабочие части.
3. Оркестратор назначает каждому `mc_implementer` ожидаемый результат и исключительный список принадлежащих ему путей.
4. Независимые исполнители могут работать параллельно. Части с общим файлом или интерфейсом выполняются последовательно.
5. Оркестратор ждёт все результаты, проверяет diff и самостоятельно выполняет интеграцию.
6. `mc_reviewer` проводит независимое ревью итогового состояния. Подтверждённые замечания исправляются до сохранения результата.
7. Оркестратор запускает подходящие проверки, проверяет staging, создаёт один содержательный коммит и выполняет `git push origin main`.

Все агенты используют общий checkout. Поэтому пишущим агентам запрещено менять чужие пути, выполнять широкое форматирование, откатывать незнакомые изменения, переключать ветки или работать с Git-историей. `git add`, `git commit` и `git push` выполняет только оркестратор.

## Матрица проверок

| Изменение | Обязательный минимум |
|---|---|
| Документация или конфигурация Codex | Проверка синтаксиса конфигурации, `git diff --check`, независимое ревью diff. |
| Локальная логика приложения | Тесты изменённого модуля, затем подходящие общие проверки и ревью. |
| БД, ограничения целостности или расчёты | Тесты модуля, полный набор тестов приложения и БД, усиленное ревью, итоговый прогон на VM. |
| Аутентификация, секреты, внешние API | Целевые негативные сценарии, полный подходящий набор тестов, security review и итоговый прогон на VM. |
| Пользовательский поток или развёртывание | Сквозной сценарий и проверка службы на VM после доставки ветки `main`. |

Если проверка неприменима или недоступна, оркестратор не выдаёт её за пройденную и явно фиксирует ограничение в итоговом отчёте.

## Примеры

Запрос: «Исправь опечатку в README».

Ожидаемое поведение: основная задача выполняет изменение без исследователя и исполнителей, затем передаёт итоговый diff агенту `mc_reviewer` и только после ревью сохраняет результат.

Запрос: «Добавь налоговые настройки и подключи их к финансовому расчёту».

Ожидаемое поведение: исследователь строит карту схемы, серверной логики и тестов; оркестратор выделяет только действительно независимые части, назначает непересекающиеся пути исполнителям, интегрирует результат, запускает усиленное ревью и полный прогон на VM.

Запрос: «Проверь текущую ветку на ошибки и проблемы безопасности».

Ожидаемое поведение: оркестратор параллелит независимые read-only направления проверки, ждёт все отчёты и возвращает единый список подтверждённых замечаний по приоритету.
