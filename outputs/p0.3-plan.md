# Marketplace Control — план P0.3

Актуально на 21 сентября 2026 года. Статус: выполняется; воспроизводимый консервативный контур реализован, финансовая и налоговая методика остаются частично заблокированы до подтверждения.

Этот файл является рабочим планом этапа P0.3 «Финансовая методика и расчёт». Он фиксирует границу этапа, обязательные решения перед реализацией, порядок работ и критерии приёмки. Чек-лист будет обновляться после каждой завершённой части.

Все формулы, обозначения, правила округления и статусы готовности собраны отдельно в каноническом документе [«Формулы финансового расчёта»](financial-formulas.md).

До реализации необходимо пересмотреть этот документ по требованиям ниже: текущие правила знаков, классификации и сверки не считаются подтверждённой методикой только потому, что уже записаны в формулах или реализованы в импорте.

## Цель

Создать воспроизводимый финансовый расчёт по выбранным товарам и загруженной истории магазина. Каждый опубликованный результат должен закреплять версию методики и точные версии входов, объясняться до исходных операций и пользовательских данных и честно сообщать о неполноте.

P0.3 заканчивается исполняемым расчётом и атомарной публикацией. Подключение реальных сумм к странице «Обзор» относится к P0.4, пользовательская расшифровка по SKU — к P0.5.

## Источники расчёта и граница печатных документов

- Рабочий расчёт использует данные API WB и внутренние данные проекта: себестоимость, дополнительные расходы, налоговые настройки и выбранные товары. Печатная форма не является входом расчёта, не входит в его fingerprint и не требуется для запуска или публикации.
- Детализация еженедельных отчётов — источник операций; сводные суммы списка отчётов API — отдельный источник контроля. Дневные и недельные отчёты нельзя складывать как независимые начисления. Периодичность `period` не следует смешивать с типом `reportType` (основной / по выкупам); покрытие типов фиксируется явно.
- Селлер самостоятельно использует свой печатный финансовый документ для проверки наших результатов. Доступ приложения к таким документам и обязательная загрузка PDF не предусматриваются в P0.3.
- Добровольно предоставленные формы используются только для отладки и тестирования методики: сначала расчёт по API, затем сравнение сопоставимых показателей с документом, без подстановки или подгонки сумм.
- Отсутствие печатной формы не создаёт `source_unreconciled`, не понижает качество и не блокирует публикацию. Ошибки, выявленные при тестовой сверке, исправляются в методике с отдельными regression-тестами.
- Отчёты хранения и приёмки могут служить расшифровкой уже учтённых расходов; их суммы нельзя повторно добавлять к расходам из финансовой детализации.

### Согласованный тестовый период

Пользователь подтвердил период уже предоставленной печатной формы: **2026-07-13 — 2026-07-19 включительно**. Это первый локальный тестовый образец, а не обязательный вход продукта. Пользователь может предоставлять формы за другие периоды для расширения тестового покрытия.

Для сверки необходимо сопоставить документ с данными API того же магазина, идентификатора и типа отчёта, валюты и отчётного периода; совпадения дат недостаточно. Сверку по строкам пока не считать выполненной. Номер документа, его суммы, реквизиты, PDF и исходные персональные выгрузки остаются вне Git; в репозитории хранится только описание сценария и синтетические regression-тесты.

## Обязательные свойства результата

- Деньги считаются как точные десятичные значения PostgreSQL `numeric(20,4)`, без арифметики через JavaScript `Number`.
- Доходы положительны, расходы отрицательны; отсутствующее значение не заменяется нулём.
- В расчёт входит только подтверждённый набор товаров и только одна принятая версия каждого отчёта WB.
- `forPay` используется только для сверки перечисления за товар и не становится дополнительным доходом или итоговой выплатой после всех расходов. Комиссию и платёжные услуги, уже включённые в него, повторно не вычитать.
- Результат разделяет товарные строки выбранного набора и доказуемые общие строки магазина. Компоненты WB без связи с товаром не приписываются SKU автоматически.
- Каждая строка результата равна сумме сохранённых доказательств: финансовых компонентов, версий себестоимости, расходов или типизированного налогового вычисления.
- Исправление отчёта, себестоимости, расхода или налоговой настройки создаёт новый результат и не меняет старую публикацию.
- Новая публикация становится текущей атомарно; предыдущая остаётся в истории.
- Нераспознанные операции, отсутствующая себестоимость и неподдерживаемая налоговая методика дают стабильные причины неполноты.
- Пилотный налоговый показатель называется «Расчётный налог УСН по доступной базе до уменьшений», а не «Налог к уплате».
- Общие расходы магазина и налог не распределяются по SKU без явно принятой методики.

## Выявленные разрывы текущего контракта

Существующие `calculation_runs`, `calculation_inputs`, `result_lines`, `result_evidence`, `reconciliation_checks` и `publications` остаются основой, но до реализации движка нужна отдельная миграция.

1. `calculation_inputs` и `result_evidence` не фиксируют версию налоговой настройки и налоговое вычисление.
2. `result_lines.product_id NOT NULL` и проверка доказательств несовместимы с общим расходом магазина, у которого `product_id IS NULL`.
3. `selection_id` не является историческим снимком: добор товаров меняет состав того же выбора.
4. Неудачный запуск нельзя безопасно повторить с тем же fingerprint из-за текущего уникального ограничения.
5. Доказательство себестоимости содержит цену и количество, но не доказывает источник количества и связь возврата с исходной продажей.
6. Налоговая настройка действует на бизнес, а расчёт и публикация сейчас относятся к магазину; смысл результата для нескольких магазинов нужно закрепить явно.
7. Текущее представление `current_daily_results` не возвращает качество, причины неполноты, период и версию методики; read-контракт для P0.4 нужно подготовить без реализации самого обзора.
8. Финансовые компоненты WB могут не иметь `product_id`; текущая модель не определяет, являются ли они общими расходами магазина, потерянной связью с товаром или исключённой строкой.
9. Текущая публикация не отделена от последнего желаемого поколения входов, поэтому после изменения данных старый результат может выглядеть актуальным до завершения нового run.
10. Импорт пропускает неизменившийся checksum до учёта новой версии нормализации. Исправление классификатора само по себе не исправляет компоненты старых отчётов; необходима версионная повторная обработка исходных данных.
11. Классификация по подстрокам и принудительный `abs` не сохраняют смысл корректировок и сторно. Ненулевые денежные поля вне текущего набора могут остаться без компонента и без причины неполноты.

## Решения, обязательные до миграции

### Классификация и период

- Сверить точные пары `docTypeName` + `sellerOperName`, компоненты и знаки на реальных данных API WB. Слово «возврат» в названии компенсации не означает возврат проданной единицы товара.
- Разделить `ppvzSalesCommission`, `vw`, `vwNds` и `ppvzReward`: это не взаимозаменяемые суммы комиссии. Для `additionalPayment` и `deduction` сохранить направление исходного знака: положительное удержание и отрицательная выплата продавцу, без безусловного `abs`.
- Зафиксировать правила для всех ненулевых денежных полей, включая лояльность и изменение срока перечисления. Неизвестное поле или неподтверждённое правило не должно молча давать полный результат.
- Проверить отсутствие двойного учёта `rebillLogisticCost`, скидок и расходов, уже включённых в другие показатели. Не считать возмещение перевозки новым расходом по одному названию поля.
- Зафиксировать allowlist операций, которые разрешено публиковать, и перечень операций, которые делают результат неполным.
- Для каждого компонента без `product_id` зафиксировать один типизированный исход: подтверждённый store-level компонент, ожидаемая товарная строка с потерянной связью либо исключённая информационная/сверочная строка.
- Подтверждённые store-level компоненты включать только в отдельный итог магазина. Компонент с ожидаемой товарной связью исключать из товарного итога и отмечать `product_link_missing`; скрытое распределение запрещено.
- Разделить сверки API: перечисление за товар (`forPay` / `forPaySum`), итог к оплате (`bankPaymentSum`) и отдельные суммы расходов. Для каждой определить состав строк, знаки и покрытие; не приравнивать общую сумму финансовых компонентов к `forPay`. Проверки полного отчёта выполнять отдельно от selected-products и store-level итогов; `bankPaymentSum` не доказывает фактическое поступление денег в банк.
- Формулу поддержки для печатного вознаграждения рассматривать только как тестовую проверку соответствующего документа, не как формулу прибыли. До её применения подтвердить соответствие колонок API, значение «логистика РФ» и обработку сервисных строк с пустым типом документа; универсальный фильтр «продажи минус возвраты» на все расходы не переносить.
- Подтвердить `rrDate` как учётную дату и правила включения строк на границе периода.
- Первый расчёт выполнять как полный пересчёт принятой загруженной истории магазина; дневные строки позволят P0.4 читать произвольный доступный период без изменения опубликованного run.

Реальные выгрузки, токены и персональные данные в Git не добавляются. Для regression-тестов создаётся минимальный обезличенный синтетический fixture только после сверки.

### Себестоимость возврата

- Использовать стоимость на дату исходной продажи только при доказуемой типизированной связи возврата с продажей.
- Не связывать строки одной эвристикой по `srid`: он не гарантированно уникален.
- Если исходная продажа не найдена однозначно, не публиковать восстановление себестоимости как полное и добавить причину `return_original_sale_unmatched`.

### Дополнительные расходы

- Расход `on_date` признавать в указанную дату.
- Расход `evenly_over_period` делить по календарным дням с точностью четыре знака; остаток округления детерминированно относить на последний день периода.
- Расход конкретного товара оставлять на уровне товара. Общий расход магазина хранить на уровне магазина, не размазывая по выбранным товарам.
- Если период расхода пересекает расчёт частично, включать только дневные доли внутри расчётного периода.

### Налог

- До реализации зафиксировать allowlist компонентов налоговой базы УСН «Доходы», правила возвратов и учётную дату каждого вклада.
- Сохранять версию налоговой настройки, базу, ставку, рассчитанную сумму и доказательства каждого вклада базы.
- Для `usn_income_expenses` и `osno` возвращать `tax_method_unsupported` без приблизительной формулы.
- НДС не считать автоматически. Для `vat_mode != exempt` результат остаётся неполным с отдельной причиной, даже если справочный расчёт УСН возможен.
- Для нескольких магазинов показатель остаётся расчётом по доступной базе выбранных товаров конкретного магазина и не называется налогом бизнеса к уплате.

### Качество результата

До реализации закрепить закрытый перечень кодов как минимум для:

- `cost_missing`;
- `return_original_sale_unmatched`;
- `operation_unclassified`;
- `product_link_missing`;
- `tax_setting_missing`;
- `tax_method_unsupported`;
- `vat_method_unsupported`;
- `report_coverage_incomplete`;
- `source_unreconciled`.

`partial` означает, что доказуемая доступная часть рассчитана, но перечислены исключённые или отсутствующие данные. `unavailable` означает, что доказуемую сумму для выбранного scope публиковать нельзя. Техническая ошибка выполнения завершает run как `failed`, а не маскируется причиной качества.

Успешный run с качеством `unavailable` публикует текущий envelope без вводящей в заблуждение итоговой суммы и атомарно supersede-ит предыдущую публикацию. P0.4 обязан читать качество текущего envelope до сумм. Технически failed run не заменяет последнюю успешную публикацию, но read API сравнивает её поколение с последним желаемым fingerprint и возвращает состояние `stale`/`failed`, а не старую сумму как актуальную. Допустим краткий переход без актуальной суммы; недопустима выдача устаревшей суммы без явного статуса.

## Критерии приёмки

P0.3 завершён, когда выполняются все условия:

1. Для магазина с выбранными товарами и принятыми отчётами создаётся неизменяемый run с версией методики и snapshot товаров.
2. Все использованные версии отчётов, себестоимости, расходов и налоговой настройки перечислены среди входов.
3. Каждая опубликованная сумма сходится с доказательствами; один источник нельзя учесть дважды.
4. Продажи, возвраты, компоненты WB, смена себестоимости и налоговой ставки на границе дат проходят regression-тесты.
5. Общий расход магазина учитывается без скрытого распределения по SKU.
6. Отсутствующая себестоимость, неоднозначный возврат, неизвестная операция и неподдерживаемый налог дают ожидаемый quality и стабильный код причины.
7. Одинаковый набор входов идемпотентен; исправленный вход создаёт новую публикацию, не меняя старую.
8. При конкурентном запуске текущей остаётся ровно одна публикация.
9. RLS и роли запрещают cross-tenant чтение и запись для snapshot, входов, налоговых вычислений и доказательств, строк результата, requests, runs и publications; DB API отклоняет несовпадающие business/store/run и запуск без разрешённой роли.
10. Классификация и контрольные суммы сверены с реальными данными API WB. При наличии добровольно предоставленной печатной формы выполнена отдельная тестовая сверка сопоставимых показателей; её статус не подменяет качество рабочих данных API.
11. Полный набор проверок проходит на VM без Docker, служба остаётся работоспособной.
12. Добор товара и изменение входа во время running run не теряются: устаревший run не становится current, а последнее поколение в итоге получает публикацию либо наблюдаемый failed/unavailable статус.
13. Отсутствие, добавление или удаление локальной тестовой печатной формы не меняет входы, fingerprint, суммы и качество рабочего расчёта и не препятствует его запуску или публикации.
14. Неизменившийся raw-отчёт повторно обрабатывается новой нормализацией; старый результат воспроизводится, новые компоненты не смешиваются со старыми и не удваивают суммы.

## Проверки

Локально как быстрые проверки:

```powershell
npm test

```

На настоящем PostgreSQL и итоговой VM:

```bash
P03_INTEGRATION_DATABASE_URL=postgresql:///marketplace_control_p03_test node db/tests/p03-app.integration.mjs
node --test app/*.test.mjs
npm --prefix db test
systemctl --no-pager --full status marketplace-control.service
curl -fsS http://127.0.0.1:3000/health
```

Интеграционный тест обязан отказываться от запуска, если имя БД явно не содержит `test`.

## Порядок реализации

Критический путь: сверка методики → контракт и миграция → чистый расчёт → DB-оркестрация → запуск и статус → полная приёмка.

После фиксации контракта чистый расчётный модуль можно разрабатывать параллельно с миграцией в непересекающихся файлах. `app/db.mjs`, миграция и интеграционный тест должны иметь последовательное владение. Изменения `app/server.mjs` и `app/frontend/pages.mjs` нельзя параллелить с P0.4/P0.5, поскольку эти этапы затрагивают те же маршруты и публичный read-контракт.

## Главные риски

- Без реальной сверки классификации WB нельзя объявлять финансовый результат полным.
- Без доказуемой связи возврата с продажей нельзя корректно восстановить его себестоимость.
- Ошибка в scope налога может превратить справочный показатель магазина в ложный «налог бизнеса».
- Скрытое распределение общих расходов по SKU создаст недоказуемую товарную прибыль.
- PGlite не проверяет конкурентные блокировки как настоящий PostgreSQL; конкурентная публикация обязательно тестируется на VM.
- Исходные зашифрованные файлы и PostgreSQL должны резервироваться согласованно, иначе полное воспроизведение результата невозможно.
