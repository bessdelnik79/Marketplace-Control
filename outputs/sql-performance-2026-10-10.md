# SQL: JIT и индексы — 10 октября 2026

Исправлена подтверждённая нагрузка компиляции SQL и отсутствующие индексы финансового чтения. Формулы, публикации, данные и правила RLS не изменены.

## Изменения

- Общая фабрика `createApplicationPool` задаёт `jit=off` при открытии каждого соединения основного пула и отдельного пула оперативных lease-блокировок. Разбор строки подключения выполняет `pg`; остальные параметры, их приоритет и защита паролей в ошибках сохранены. Глобальная настройка PostgreSQL не меняется, дополнительных SQL-команд на каждый запрос нет.
- Миграция 082 создаёт B-tree индексы `financial_daily_evidence(daily_result_id,id)` для доказательств дневного результата и `operation_versions(report_normalization_id,accounting_date)` для операций замороженной нормализации. Оба соответствуют существующим фильтрам и порядку чтения.
- Порядок применения и кратковременная блокировка записи при построении описаны в [документации БД](../db/README.md). Словарь БД после проверки не изменился.

## Замеры и проверки

На действующей БД одинаковый SELECT списка магазинов проверен через `EXPLAIN (ANALYZE,BUFFERS)` под ролью приложения и с его контекстом доступа. В исходном прогретом замере SQL занимал около 80 мс, из них 78 мс — JIT; с отключённым JIT — около 0,9 мс. Повторный замер перед развёртыванием: 216,148 мс с JIT (компиляция 82,862 мс), 1,026 мс без JIT. Время зависит от прогрева; это время SQL, а не HTTP-страницы. Вызов `listStores` исправленным кодом после первого подключения занимал 6,9–10,7 мс.

Проверки на выделенной VM, напрямую без Docker:

- приложение: 799/799 тестов, включая параметры подключения и сокетные DSN;
- схема: 180 проверок, включая валидность и порядок ключей обоих индексов;
- финансовая PostgreSQL-интеграция P0.3: 13/13;
- оперативный кэш финансовых возвратов: 11/11 под обычной ролью `NOSUPERUSER NOBYPASSRLS`;
- обновление заполненной одноразовой БД с версии 81 до 82 сохранило контрольные суммы финансовых доказательств и операций; индексы доступны под обычной ролью с FORCE RLS;
- новый основной пул и фактический отдельный пул lease-блокировок имеют `jit=off`, тогда как настройка самого PostgreSQL остаётся `on`.

Независимое ревью завершено без блокирующих замечаний. Локальные 799 тестов также прошли. Повторные запросы финансового обзора и расширение SQL-наблюдаемости остаются отдельными задачами исходного аудита; эта правка охватывает JIT и два подтверждённо отсутствовавших индекса.

## Устранение повторных проходов по операциям SKU

После миграции 082 проверены реальные процессы списка SKU, карточки, вкладов и проверки доказательств поколения. `financial_daily_evidence` использует новый индекс по результату. Исторические 38 тыс. сканирований и 1,23 млрд прочитанных строк нельзя считать текущей скоростью нагрузки: оценивать нужно новые планы и прирост счётчиков.

В метаданных SKU обнаружена сохранявшаяся причина нагрузки: под RLS условие `operation.id=coalesce(f.operation_version_id,e.source_operation_version_id)` не становилось индексным поиском по ID. Августовский список выполнял 360 полных проходов по 11 320 операциям — около 4,1 млн проверок строк. Само наличие индекса по нормализации этот поиск по другому ключу не исправляет.

Выражение заменено на эквивалентный `CASE`: сначала ID операции финансового компонента, при его отсутствии — ID прямого источника доказательства. Сохраняются приоритет, коррелированный lookup, точные замороженные версии/нормализации, tenant/магазин, дата, товар, состояние и проверка суммы. PostgreSQL теперь использует существующий индекс `(business_id,store_id,id)` с одним точечным поиском на доказательство.

Замеры под обычной ролью приложения на действующих данных VM, при включённом обычном планировщике:

| Проверка | До | После |
|---|---:|---:|
| SQL метаданных августовского списка | 236–271 мс | 24–27 мс |
| Shared-buffer hits того же SQL | 127 700 | 12 860 |
| Доступ к операциям того же SQL | 360 полных проходов | 360 поисков по ID |
| Полный ответ списка SKU за август | 318 мс | 131 мс |
| Полный ответ списка SKU за март | 1 227 мс | 258 мс |

Полные ответы списка, карточки с недельными результатами и вкладов за март и август сравнивались целиком в памяти: все шесть пар совпали. Замеры характеризуют проверенный набор данных и состояние прогрева, а не предельную пропускную способность. Для карточек также подтверждён точечный индексный план операций.

Повторные проверки этой правки: 799 тестов приложения локально и на VM, 180 проверок схемы, 13 PostgreSQL-проверок P0.3 и 11 проверок оперативного финансового кэша. Новая native-регрессия метаданных прошла 7/7: daily/legacy, приоритет компонента и прямой fallback, количества, отсутствующие/несовместимые источники, замороженный failed-источник, чужой tenant/магазин, точные owner/date/period и индексный поиск под FORCE RLS. Каждый поиск читает не более одной строки операции при обычном планировщике. Тот же тест с исходным `COALESCE` сохраняет функциональные результаты, но проваливает обе проверки плана из-за `Seq Scan`; это подтверждает обнаружение регрессии нагрузки. Независимое ревью не выявило блокеров.

## Проверка CPU при открытии Обзора

На VM с двумя CPU, PostgreSQL 18.6 и развёрнутым `2d28860` выполнены ограниченные чтения действующих данных под ролью приложения с его RLS-контекстом; `jit=off` подтверждён. В памяти использован только разрешённый `DATABASE_URL`, без вывода и сохранения. Очереди, публикации и данные не изменялись, WB не вызывался.

Воспроизведена функция маршрута `GET /overview` вместе с настоящими readers и HTML-рендерером в отдельном диагностическом процессе Node на VM. Авторизация HTTP и передача по сети в длительность не входят. Для POST обновления измерены финансовый cache reader и эквивалентная SELECT-часть проверки очереди, без выполнения INSERT/UPDATE. Поэтому это профиль серверной работы, а не запись конкретного браузерного эпизода пользователя с показателем 75%.

| Часть | Измеренная длительность |
|---|---:|
| Обзор без явно выбранного периода, прогретое чтение | 977 мс |
| Оперативная статистика внутри него | 816 мс |
| Чтение финансовых периодов внутри него | 117 мс |
| Ситуации внутри него | 21 мс |
| HTML внутри него | 1 мс |
| Повторный GET оперативной панели | 803 мс |
| Финансовый кеш автоматического обновления | 15–18 мс |
| SELECT-проверка очереди автоматического обновления | 407–413 мс |

Обзор выполняет 110 команд БД без HTTP-авторизации, включая BEGIN/COMMIT и установку контекста; финансовая часть — 70. У явно выбранных марта/августа: 85 команд и 962–968 мс, из которых оперативное чтение занимает 804–806 мс. Найдены 39 повторов одинакового SQL с одинаковыми параметрами в стандартном Обзоре, но часть — обязательные команды транзакций/контекста, поэтому это не 39 автоматически удаляемых запросов.

Основная стоимость — два SELECT из `current_operational_daily_metrics`: показатели и прогресс всей фабрики истории (`operational.repository.mjs:548`, `:516`). В EXPLAIN ANALYZE они занимают 395–402 и 362–398 мс соответственно. Проекция тех же строк без полей возвратов занимает 3–7 и 2,6–2,8 мс. Все блоки находятся в shared buffers, чтение с диска — ноль; генерация дней, сортировка и индексный поиск самих показателей занимают единицы миллисекунд. Малые последовательные сканирования таблиц snapshots не объясняют основную стоимость.

Представление отдельно вызывает `operational_financial_return_refs_current` для количества и суммы возвратов (`070_operational_return_source.sql:64`). В первом SELECT 198 финансовых строк имеют только четыре различных `return_source_refs`: одни проверки повторяются по товарам, дням и двум полям. Диагностический SELECT с MATERIALIZED-набором уникальных refs и одной проверкой каждого набора занимает 7,6–8,2 мс. Это подтверждает направление оптимизации; такой SELECT ещё не является полной заменой рабочего reader и не доказывает время будущего полного ответа.

CPU измерен по приращению utime/stime процессов. Один Обзор потребляет 0,87–0,97 секунды CPU PostgreSQL и 0,08–0,13 секунды CPU диагностического Node. Два ограниченных одновременных чтения оперативной статистики потребили 1,59 секунды CPU PostgreSQL за 0,858 секунды — около 93% суммарной мощности двух CPU. Одновременность конкретных пользовательских HTTP-запросов не зафиксирована; показание 75% из интерфейса VM не было воспроизведено как тот же самый эпизод.

Клиент после открытия страницы немедленно отправляет POST `/overview/operational-refresh`, затем GET панели (`ui.js:76`, `:87`, `:89`), включая уже актуальную панель. Pending/running/waiting-financial продолжают polling каждые 10 секунд. После ошибки/15-секундного timeout POST может повторяться через 10 секунд, поскольку флаг `refresh=false` устанавливается только после успеха. На измеренном наборе SELECT проверки очереди занимает менее секунды; наложение из-за timeout здесь не подтверждено.

Приоритет исправлений:

1. Проверять уникальную комбинацию business/store/полных financial refs один раз в пределах SQL-оператора и использовать результат для обоих полей и всех соответствующих строк. Сохранить invoker RLS, точную проверку актуальности версий и NULL для недостоверного возврата. Не применять бессрочный кеш и не убирать проверки возвратов.
2. Устранить повторное тяжёлое чтение для прогресса и GET панели после актуального первоначального HTML. Ограничить автоматическое обновление по свежести и состоянию, сохраняя восстановление отсутствующих дней и реакцию на новые финансовые источники.
3. Затем убрать повторную загрузку текущего/предыдущего финансового периода при поиске последней недели и повторное чтение текущего периода для ситуаций; переиспользовать данные только с той же замороженной идентичностью публикации и периодом.

В этой проверке код приложения и схема не изменены. Проверены runtime-чтения и планы на VM; повторный полный набор unit/schema-тестов для отчёта не запускался.
