# Marketplace Control — план событийной загрузки и пересчёта финансов

Актуально на 28 сентября 2026 года.

Этот документ фиксирует следующий архитектурный этап после P0.3/P0.4: устойчивую загрузку финансовых отчётов WB, локальный событийный пересчёт и дневную read-модель. Текущее поведение описано в [«Финансовых отчётах Wildberries»](financial-reports.md), финансовая методика — в [«Формулах финансового расчёта»](financial-formulas.md), проверенные контракты — в [планах P0.3](p0.3-plan.md) и [P0.4](p0.4-plan.md).

Статус выполнения: этапы 1–5 реализованы. Durable queue, credential generation, недельный ledger, list-first inventory, понедельничное расписание, адресный raw/version pipeline и локальная дневная generation работают. После обязательной shadow-сверки `financial-result-v20` атомарный pointer переключает period read на дневную модель; пока publication строится, обзор сохраняет предыдущие суммы и показывает статус обновления.

## Цель

Разделить четыре независимых процесса:

1. обнаружение и загрузку исходных отчётов WB;
2. локальную нормализацию сохранённой версии отчёта;
3. расчёт затронутых календарных дат;
4. атомарную публикацию новой финансовой generation.

Выбор периода, изменение налога, себестоимости, ручных расходов, выбранных товаров или версии методики не должны обращаться к WB. Они используют уже сохранённые `report_versions`. Пока новая generation строится, пользователь продолжает видеть предыдущий опубликованный результат с явной отметкой «Обновляется».

## Зафиксированные продуктовые правила

### Год после подключения ключа

- При первом успешном сохранении WB API-ключа создаётся план загрузки финансовых отчётов за один календарный год.
- При фактическом изменении ключа создаётся новая `credential_generation` и весь год проверяется заново как явная проверка актуальности.
- Повторное сохранение того же ключа не создаёт новую generation и не запускает год повторно.
- Год — полные недельные периоды WB `понедельник–воскресенье`, пересекающие интервал от московской календарной даты события минус один год до последнего закрытого воскресенья. В зависимости от границ это 52 или 53 недели. Незакрытая текущая неделя не объявляется полной.
- Загрузка исходников не зависит от выбора товаров. Выбор SKU остаётся условием расчёта и публикации, но не получения и хранения отчётов.

### Понедельничное расписание

- Каждый понедельник в `00:00 Europe/Moscow` для всех активных подключённых WB-магазинов с доступом к финансам создаётся задание на предыдущую закрытую неделю.
- Пропущенное из-за остановки приложения расписание догоняется ровно один раз после запуска.
- Пустой ответ WB сразу после полуночи не доказывает отсутствие отчёта и не закрывает покрытие. Задание повторяется с backoff до появления отчёта или до диагностируемого терминального состояния.
- Пять последних закрытых недель считаются свежими и явно перепроверяются по понедельникам. Более старые недели запрашиваются только при первой/изменённой учётке, доказанном пробеле покрытия или ручной проверке актуальности.

### Когда разрешён WB API

Обращение к WB разрешено только при одном из оснований:

- отсутствует ожидаемый исходный отчёт;
- есть доказанный разрыв покрытия;
- выполняется явно запланированная проверка актуальности: новая `credential_generation`, понедельничная проверка свежих недель или ручной refresh;
- WB сообщил новый `reportId` либо после проверки checksum детализации отличается от сохранённой версии.

Изменение налога, себестоимости, расхода, выбора товаров или методики не является основанием для WB-запроса.

## Стратегия запросов WB

Основной сценарий использует двухступенчатую схему:

1. `sales-reports/list` запрашивает инвентарь отчётов за год или за проверяемое свежее окно. До 1000 отчётов помещаются в одну страницу; при необходимости используется `offset`.
2. Детализация загружается адресно по каждому нужному `reportId`: отсутствующему либо включённому в явную freshness-проверку. Пагинация идёт по `rrdId` до ответа `204`.

Один широкий запрос детализации за год технически допустим, но не является основным сценарием: он создаёт крупную единицу повтора, откладывает обработку первых недель до завершения всего потока и не даёт надёжно считать отдельную неделю завершённой до финального `204`.

Если методы списка или детализации по `reportId` недоступны для страны регистрации продавца, используется совместимый fallback: детализация за недельный период. Выбор capability фиксируется в состоянии подключения, а не определяется случайной повторной попыткой каждого задания.

Для каждой принятой детализации вычисляется канонический checksum. Совпавший checksum не создаёт новую `report_version` и не запускает пересчёт; отличающийся checksum создаёт неизменяемую версию и событие изменения. Ограничение WB на один запрос в минуту на кабинет соблюдается через общий PostgreSQL rate slot. Разные кабинеты можно обрабатывать параллельно, один кабинет — последовательно.

## Целевая цепочка

```text
credential/schedule
  -> report inventory
  -> detail fetch
  -> immutable raw + report_version(received)
  -> local normalization
  -> report accepted/updated event
  -> affected-date recalculation
  -> unpublished daily generation
  -> atomic publication pointer switch
```

### 1. Устойчивая PostgreSQL-очередь

Использовать существующую `mc.jobs`, которая пока не задействована runtime-кодом, вместо второй общей очереди.

Обязательный контракт:

- статусы `pending`, `running`, `succeeded`, `failed`;
- атомарный claim через `FOR UPDATE SKIP LOCKED`;
- `available_at`, приоритет, число попыток, `max_attempts`;
- lease token, `lease_until`, heartbeat и возврат просроченного `running` в повтор;
- стабильный deduplication key;
- retry с backoff для временных ошибок и terminal `failed` после исчерпания попыток;
- безопасный результат `superseded` внутри завершённого задания, если его credential/event generation устарела;
- внутренний межтенантный claimant с узкими `SECURITY DEFINER`-функциями, аудитом и сохранением RLS пользовательских чтений.

Типы заданий первого контура:

- `financial_inventory_refresh`;
- `financial_report_fetch`;
- `financial_report_normalize`;
- `financial_dates_recalculate`;
- `financial_generation_publish`.

### 2. Планировщик покрытия

Нужен недельный ledger по магазину:

- `week_start`, `week_end`;
- причина проверки;
- `credential_generation`;
- ожидаемые и найденные `reportId`;
- состояние coverage отдельно от состояния job;
- `last_checked_at`, `freshness_due_at`;
- последняя успешная версия/контрольная сумма;
- ошибка и время следующей попытки.

Успешный пустой HTTP-ответ сам по себе не переводит неделю в complete. Покрытие становится полным только после подтверждения инвентарём WB и успешного приёма всех ожидаемых отчётов либо после отдельного доказуемого правила «закрытая неделя без отчёта».

При годовой загрузке задания создаются для всех 52/53 недель, но актуальная понедельничная неделя имеет больший приоритет. Каждая завершённая неделя сразу запускает дальнейшую обработку; весь год ждать не нужно.

### 3. Версия учётных данных

Фактическое изменение ключа определяется стабильным HMAC-fingerprint с доменным префиксом; AES-GCM ciphertext для сравнения непригоден из-за случайного nonce.

В одной транзакции должны происходить:

- сохранение нового шифротекста;
- увеличение `credential_generation` только при отличающемся fingerprint;
- создание события подключения/изменения;
- постановка годового inventory refresh.

Задание старой generation не может принять отчёт или переключить публикацию после смены ключа.

### 4. Разделение загрузки и нормализации

Текущий `completeFinancialSync()` должен быть разделён:

- fetch сохраняет защищённый исходник, страницы, `reports`, `report_versions(status='received')` и ставит normalize-job;
- normalize-job локально создаёт `report_normalizations`, операции, компоненты, issues и reconciliation checks;
- только успешная нормализация в одной транзакции переводит версию в `accepted`, переключает `reports.current_version_id` и создаёт `report_accepted` либо `report_updated`;
- ошибка нормализации не меняет предыдущую принятую версию;
- новая версия парсера перенормализует сохранённые `report_versions` без WB API.

### 5. События и затронутые даты

Событие и pending-job создаются транзакционно вместе с изменением входа, чтобы не было lost wakeup.

| Событие | Затронутый диапазон | WB API |
|---|---|---|
| Принят или изменён отчёт | Период отчёта | Уже выполнен fetch |
| Изменилась себестоимость | От `effective_from` до следующей версии | Нет |
| Изменился расход | Даты признания версии расхода | Нет |
| Изменилась налоговая настройка | От даты действия по всем активным магазинам бизнеса | Нет |
| Изменился набор товаров | Всё применимое сохранённое покрытие | Нет |
| Новая версия нормализатора | Отчёты без этой нормализации | Нет |
| Новая версия расчётной методики | Всё применимое сохранённое покрытие | Нет |

Пересекающиеся invalidation-события объединяются, но их исходные причины и диапазоны остаются в append-only журнале.

## Дневной финансовый слой

Новая immutable generation должна хранить:

- точные суммы `numeric(20,4)` по календарной дате, категории, scope и при необходимости товару/варианту;
- дневное coverage;
- дневные `quality` и причины неполноты с областью применимости;
- frozen manifest версий отчётов, нормализаций, себестоимости, расходов, налогов и selection;
- версии parser/result method;
- evidence для каждой суммы;
- неокруглённые налоговые базы/numerators.

Причина уровня недельного отчёта применяется ко всем дням его периода, а не только к датам строк. Нельзя переносить range-wide quality на произвольный срез `result_lines`.

Произвольный период читается без пересчёта:

- сначала проверяется непрерывное дневное coverage;
- суммы агрегируются точным `SUM`;
- итоговая quality — худшая только среди выбранных дней;
- missing reasons — distinct union только выбранных дней;
- scope и версии обязаны быть совместимы;
- налог агрегируется по сохранённым базам/numerators и округляется по SKU по действующему контракту, а не складывается из отдельно округлённых дневных налогов.

Недельные результаты дневного слоя должны совпасть с проверенными P0.3 period results по суммам, quality и причинам до переключения read path.

## Атомарная публикация и интерфейс

Worker строит generation вне current pointer. Публикация в короткой транзакции:

1. блокирует магазин;
2. проверяет credential/event generation и frozen input fingerprint;
3. отклоняет устаревший результат;
4. помечает generation успешной;
5. атомарно переключает current publication.

До переключения предыдущая публикация остаётся доступной. Overview возвращает её вместе с отдельным состоянием обновления:

```text
updateStatus: pending | running | failed | null
updateStartedAt
lastUpdateError
affectedPeriod
```

UI показывает прежние суммы, их фактическую свежесть и badge «Обновляется»/«В очереди». Ошибка обновления не превращает существующую публикацию в `unavailable`. Если публикации ещё никогда не было, сохраняется честное пустое состояние.

`getPublishedFinancialPeriod` переходит на дневную generation только после shadow-проверки. Exact-range расчёт из overview GET после переключения удаляется. Уведомление о зарубежном выкупе остаётся информационным: оно не меняет суммы, quality или missing reasons и определяется только по принятым отчётам `reportType=2` с нероссийской `country`.

только сохранённые `report_rows`, а приёмка версии, недельного ledger,
append-only события и `financial_dates_recalculate` происходит атомарно.
Пустой detail не закрывает coverage. Обработчик локального пересчёта относится

### Этап 4. Локальные события и дневная generation

- [x] Перевести отчёты, себестоимость, расходы, налоги, selection и совместимые method bump на общий event/outbox.

- [x] Запустить shadow backfill из сохранённых `report_versions` без WB API.
- [x] Сверять каждую опубликованную неделю с конкретными P0.3 publication/run/period result.

Изменение локального входа атомарно добавляет append-only событие и
`financial_dates_recalculate`; pending-события coalesce в одном job, а при
уже запущенном predecessor его диапазон переносится в successor. Исходные
причины при этом остаются в журнале. Worker строит
неизменяемую generation только по сохранённым версиям, хранит непрерывное
дневное coverage, evidence и точные неокруглённые налоговые numerators, а
налог округляет один раз на SKU при агрегации периода. До первого переключения
результат остаётся shadow: сравнение записывается для точной legacy publication
и не меняет `mc.publications` или WB queue. После успешного gate этапа 5 дневная
publication становится отдельным авторитетным read-источником, не изменяя
legacy history.
Первичный backfill охватывает union всех опубликованных period results
магазина, а не только текущую публикацию. Новая parser/result method получает
события лишь после явного compatibility gate: неизвестная версия не может
тихо рассчитаться формулами v11/v20.

- [x] Реализовать stale-while-revalidate UI и polling до новой publication либо terminal job.
- [x] Удалить расчёты и постановку заданий из overview GET; compatibility `Map` удалить после итоговой VM-приёмки durable worker на этапе 6.

Первая публикация допускается только для generation `financial-result-v20`,
когда каждый публикуемый день покрыт matched shadow-сравнением с точной legacy
publication и идентичным набором выбранных товаров. Последующая частичная
публикация копирует неизменённые дни предыдущего pointer и заменяет только
affected range; смешивание parser/result method или product scope запрещено.
Если текущий daily pointer пересекает запрошенный диапазон, он авторитетен даже
при `unavailable`: legacy fallback не может скрыть пробел daily coverage.
Fallback используется только пока у магазина вообще нет пересечения с daily
publication. Owner/editor может повторить terminal job; повтор использует тот
же связанный job после сброса lease/attempt state. Обзор показывает старую
publication во время pending/running, опрашивает JSON status и перезагружается
при новом pointer или terminal failure.

## Критерии приёмки

1. Первый ключ создаёт ровно один годовой план; тот же ключ повторно не создаёт его, изменённый ключ создаёт новую generation и один новый план.
2. Годовой inventory охватывает 52/53 полные недели, а после каждого принятого отчёта его неделя сразу доступна дальнейшей обработке.
3. До понедельника `00:00 МСК` новая неделя не ставится; после границы она ставится для всех eligible-магазинов, включая catch-up после downtime.
4. Два процесса не выполняют одно задание одновременно; просроченный lease безопасно восстанавливается.
5. Пустой ответ WB не создаёт ложное complete coverage. `401/402`, `429`, `5xx`, timeout и задержка публикации имеют различимое поведение.
6. Неизменившийся отчёт не создаёт новую версию; изменившийся создаёт immutable `report_version` и пересчитывает только затронутые даты.
7. Изменения налога, себестоимости, расходов, selection и методики выполняют ноль WB API-вызовов.
8. После падения на любом этапе очередь продолжает работу без потери события и без двойной публикации.
9. Любой период до 366 дней читается без запуска расчёта; coverage, quality и reasons относятся только к выбранным дням.
10. Недельные суммы, налог, quality и reasons нового слоя совпадают с проверенным P0.3-контрактом.
11. Неудачная или устаревшая generation не меняет current publication.
12. Пока идёт обновление, пользователь видит предыдущую публикацию с честной свежестью и отметкой «Обновляется».
13. RLS и внутренние worker-функции не позволяют прочитать или изменить данные другого бизнеса.
14. VM-приёмка подтверждает restart recovery, отсутствие дублей, активную службу и `/health = ok`.

## Первый конкретный шаг

Первый implementation slice — только durable queue foundation:

1. `db/migrations/034_financial_event_queue.sql`;
2. schema/integration-тесты статусов, deduplication, claim, lease, heartbeat, retry и восстановления;
3. минимальный `app/infrastructure/jobs/` repository;
4. совместимый фасад в `app/db.mjs` без переключения текущих financial routes и workers.

После его независимого ревью и VM-проверки можно параллельно начинать credential/scheduler и подготовку дневной модели на уже стабильном контракте очереди.
