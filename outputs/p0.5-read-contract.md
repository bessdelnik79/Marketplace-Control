# P0.5 — контракт чтения расшифровки

Зафиксирован 4 октября 2026 года, версия `p05-drilldown-v1`. Контракт пункта 1 [плана P0.5](p0.5-plan.md); серверные readers пункта 2 реализованы в `drilldown*.mjs`. HTTP-маршруты и страницы списка, карточки и источников реализованы в пункте 3 5 октября. Финансовая методика и схема БД не изменены.

## 1. Контекст и операции чтения

Вся расшифровка читает одну публикацию. Обязательный контекст: `storeId`, `publicationSource` (`legacy` или `daily`), `publicationId`, `periodStart`, `periodEnd`. Даты включительные, календарные `YYYY-MM-DD`; бизнес определяется сервером из сессии и членства, а не из параметра клиента. Для карточки добавляется `productId`, для источников — идентификатор группы/строки и cursor.

`publicationId` идентифицирует сохранённую запись публикации в соответствующей таблице. Для legacy он фиксирует `runId`; для daily — карту опубликованных дней. Он не является ID generation, period result, текущего указателя или оперативного snapshot. После входа из обзора источник и ID передаются во всех переходах; параметры периода не могут расширить сохранённое покрытие.

Серверные операции экспортируются из `app/db.mjs` и `app/modules/calculation/drilldown.repository.mjs`:

| Операция | Вход сверх контекста | Результат |
|---|---|---|
| `readPublishedSkuList` | `search`, `sort`, `cursor`, `limit` | Страница SKU, полный scope, общие строки и контрольный итог |
| `readPublishedSkuCard` | `productId` | Тот же SKU и суммы, группы категорий, ссылки на строки и источники |
| `readPublishedContributions` | `productId` либо scope `store`, `groupKey`, необязательный `lineRef`, `cursor`, `limit`, `taxBasis` | Страница сохранённых вкладов и разрешённых полей источников; `taxBasis: true` раскрывает базу сохранённого legacy-налога |

Прямое открытие `/sku` без публикации может один раз разрешить текущий результат существующим механизмом обзора и перенаправить на полный контекст. После фиксации ID запрещены выбор «последнего», автоматический переход legacy ↔ daily и восстановление суммы из текущих входов. Несуществующая или неподдерживаемая зафиксированная публикация не заменяется другой.

Один ответ собирается в согласованном снимке БД: публикация, карта дней, scope, суммы и evidence читаются вместе в транзакции с пользовательским/RLS-контекстом. Неизменяемые записи читаются по ID. Текущее состояние обновления и доступность новой публикации — отдельные поля; они не изменяют зафиксированный результат.

## 2. Общий ответ

Список, карточка и страница вкладов возвращают одинаковый `context`:

| Поле | Значение и правило |
|---|---|
| `contractVersion` | `p05-drilldown-v1` |
| `publication` | `{ source, id, publishedAt, runId }` для legacy; `{ source, id, publishedAt, dayRefs }` для daily. `dayRefs`: точные пары `{ accountingDate, generationId }` выбранного диапазона |
| `storeId`, `period` | Проверенный магазин; `{ start, end }` запрошенного финансового диапазона |
| `method` | Сохранённый код методики и её ID; для daily дополнительно `parserMethodVersionId`, `resultMethodVersionId` каждого участвующего generation. Не текущая настройка бизнеса |
| `scope` | `type: selected_products`, опубликованные `productIds`, признак включения строк `store`; для daily — также scope каждого участвующего generation. Текущий ассортимент scope не определяет |
| `quality`, `missingReasons` | `complete / partial / unavailable` и сохранённые причины для данного периода. Глобальное качество run не подменяет period quality |
| `coverage` | Запрошенные и реально покрытые даты, полнота; для daily — наличие каждого дня и его coverage. Одного min/max недостаточно для доказательства отсутствия дыр |
| `resultBasis` | `before_tax / after_tax / unavailable`, согласно существующему опубликованному envelope и пригодности налога |
| `totals` | Сохранённые/существующим reader агрегированные `selectedProductsResultBeforeTax`, `storeLevelResultBeforeTax`, `availableResultBeforeTax`, `estimatedUsnTax`, `availableResultAfterTax`, `netProfit`; недоступное — `null` |
| `reconciliation` | Проверка денег и evidence из раздела 6; отдельно от качества финансового расчёта |
| `update` | Состояние текущего локального обновления и, если есть, ID новой доступной публикации. Новая публикация проверяется на доступ и совместимость с магазином/диапазоном |

Все суммы и количества с дробной частью передаются десятичными строками. Суммы результата и обычных вкладов имеют точность 4 знака, точные дневные налоговые значения — 12; `sourceAmount` компонента WB сохраняет исходную точность, которая может быть выше четырёх знаков. Ставка сохраняет точность своего источника; trailing zeros PostgreSQL не меняют её математическое значение или ограничения методики. `Number`/float для денежной арифметики не применяется. Отображение двух знаков не меняет данные сверки. UUID остаются ссылками, а не названием товара.

`null` означает неизвестное или неподдерживаемое, с причиной; `0.0000` допустим только при подтверждённой применимости/полноте соответствующего источника. Отсутствие строки в частичном результате само по себе не подтверждает ноль. Причины периода не размножаются на все SKU как якобы доказанные товарные причины: если причины не имеют товарной привязки, возвращаются как причины периода.

## 3. Список, карточка и вклад

Строка SKU: `productId`, доступные `name`, `sellerArticle`, `wbArticle`, `imageUrl`, признак исторического/удалённого товара; `quality`, причины с указанием области, `metrics`, `groups`. Каталог используется для подписи, а не для выбора финансовых строк. Если историческое название не сохранено, явно показывается отсутствие названия и доступный артикул; новое фото или ссылка WB не выдумываются. Метаданные каталога могут быть текущими и не выдаются за замороженный финансовый вход.

Метрики: выручка, расходы WB, себестоимость, дополнительные расходы, налог, доступный результат до/после налога. Каждая содержит `amount`, `basis`/правило знака, `availability`, причины, список `groupKeys`. При наличии подтверждённого quantity показываются количество и его источник; количество не выводится из суммы или числа evidence-строк. Несколько денежных компонентов одной операции не считаются несколькими продажами.

Карточка возвращает те же метрики SKU без иной формулы. `groupKey` задаёт scope, товар и категорию в рамках контекста; он не является persisted ID. Группа содержит знаковую сумму, количество исходных строк, `evidenceStatus`, причины недоступности доказательств, ключ для постраничного чтения. Полные коллекции `lineRefs`/tax-fact refs используются внутри reader и не выдаются в списке/карточке. Отдельный `lineRef` появляется на странице вкладов:

- legacy: `{ source: legacy, runId, periodResultId, resultLineId }`; `periodResultId: null` только для поддерживаемого старого результата без period envelopes;
- daily: `{ source: daily, accountingDate, generationId, dailyResultId }`;
- налог daily за диапазон: `{ source: daily_tax_range, productId, period, taxFactRefs }`. Это агрегат точных фактов, а не фиктивный `dailyResultId`; большую коллекцию фактов reader выдаёт страницами.

Вклад в реализации: `id` доказательства, `lineRef`, `contributionAmount`, `source`, `evidenceStatus`, `missingReasons`. `source` содержит `sourceKind`, разрешённые source IDs, учётную дату/период, исходную сумму или цену и quantity при наличии. При недоступном источнике `source: null`; сохранённый вклад остаётся видимым. `sourceAmount` не подменяет вклад в итог. Налоговая база использует `basisContributionAmount` и `taxFact` (daily) либо `taxComputationId`/`segment` (legacy); эти значения не считаются прямым вкладом денежного компонента в итог налога.

`sourceValidationScope: page` отделяет проверку источников выданной страницы от денежной сверки всей группы. `evidenceStatus: matched` допустим для полного проверенного ответа, `unchecked` — для проверенной страницы, не подтверждающей остальные страницы, `unavailable` — при конкретном пробеле/несоответствии. Каждый выдаваемый источник проверяется независимо. Legacy налоговая группа имеет `taxBasisAvailable: true`; `taxBasis: true` возвращает ограниченные страницы базовых компонентов и отдельный `taxSummary`, без вложенного полного raw/basis массива. Cursor привязан также к этому режиму.

Источник WB включает ID отчёта/строки (`reportId`, `rrdId` при наличии), frozen `reportVersionId`, `reportNormalizationId`, `operationVersionId`, при необходимости `financialComponentId` и `operationLinkId`. Для пользовательского ввода — конкретный `costVersionId`, `expenseVersionId` или `taxSettingVersionId`, дата действия и применённое правило. Идентификаторы относятся к проверенной цепочке доказательств.

Перед выдачей проверяются также товар/вариант, учётная дата и область источника относительно конкретной строки/факта, включая требования методики возвратного link. Простого совпадения business/store недостаточно для подтверждения вклада.

Поиск применяется только к опубликованным SKU: название и артикулы; сортировки `result_asc`, `result_desc`, `revenue_asc`, `revenue_desc`. Для результата используется одинаковое с карточкой основание налога; недоступное в конце, равные значения стабилизируются `productId`. `limit` по умолчанию 25, максимум 100, невалидный ввод отклоняется. `nextCursor` привязан к контексту, поиску/сортировке и последнему ключу. Вклад сортируется по дате, категории, идентификатору строки и evidence/fact ID. Смена фильтра требует нового cursor.

`totalItems` и сумма страницы относятся к поиску, `scopeItemCount`, `storeLines` и контрольные суммы — ко всему финансовому scope. Пагинация не заставляет браузер загружать весь raw-отчёт; контроль выполняется сервером по всей группе, а не только по странице вкладов.

## 4. Две цепочки доказательств

### Недельные и совместимые старые публикации

`mc.publications → calculation_runs → financial_period_results → result_lines → result_evidence`. Scope берётся из `calculation_request_products` для request соответствующего run, frozen входы — из `calculation_inputs`. У legacy-публикаций без period envelopes допускается только сохранённый точный период и доказанная поддержка адаптера; произвольный диапазон из общего качества/итога run не восстанавливается.

Для диапазона читаются только совместимые сохранённые period envelopes того же run, которые точно покрывают диапазон без дыр и пересечений. Используется существующая проверка `aggregatePublishedPeriodEnvelopes`; не применяется пропорциональное деление недель. Все `periodResultId` и `resultLineId` сохраняются в ссылках — нынешний обзорный reader их полностью не возвращает.

| Тип вклада | Обязательная цепочка |
|---|---|
| WB-компонент | `result_evidence.financial_component_id → financial_components → operation_versions → report_rows`; одновременно проверяются frozen report version и normalization данного run, а также методика компонента/нормализации |
| Возврат расходов / коррекция строки WB | Сохранённые `report_row_id`, `source_operation_version_id`, frozen версии и, когда нужен возвратный link, его наличие в `calculation_inputs`; коррекция округления остаётся отдельной строкой |
| Себестоимость | Версия цены, операция, вариант, количество; для возврата — зафиксированная связь с продажей. Текущая цена не читается вместо сохранённой |
| Дополнительный расход | `expense_version_id` из входов run, сохранённый вклад и правило признания версии |
| Налог | `tax_computation_id → tax_computations → tax_computation_segments → tax_basis_evidence → financial_components`, плюс frozen налоговая настройка каждого сегмента |

Справочный налог старой методики не объявляется включённым в результат. В частности, нынешний старый путь `financial-result-v3` способен вычислять справку при чтении; P0.5 не использует такой новый расчёт как сохранённое evidence. Если цепочка налога не сохранена, налоговое доказательство недоступно с причиной; подтверждённые остальные строки могут читаться.

### Опубликованные дневные поколения

`mc.financial_daily_publications → financial_daily_publication_days(accounting_date, generation_id) → financial_daily_days / financial_daily_results / financial_daily_reasons`. Каждая строка присоединяется сразу по generation **и** дате. `publication.generation_id` не описывает весь диапазон: публикация может сохранить дни из предыдущих поколений вне изменённого интервала.

Далее: `financial_daily_results → financial_daily_evidence → frozen source`, а входы и выбранные товары берутся из `financial_daily_generation_inputs` и `financial_daily_generation_products` того же generation. WB report version и normalization проверяются одновременно; одной версии отчёта или одного общего `srid` недостаточно. Возвратные связи проверяются по сохранённым доказательствам поколения, а не последнему найденному совпадению.

Налог: `publication_days → financial_daily_tax_facts → financial_daily_tax_evidence → financial_components → operation_versions → report_rows`; настройки — по `tax_setting_version_id` факта и frozen входу generation. Читаются `tax_base_unrounded`, `tax_numerator_unrounded`, `tax_rate_fraction`. Для каждого SKU точные числители выбранных дней суммируются, затем округляются по существующему `aggregateDailyFinancialGeneration`; итоговый налог — сумма этих SKU. Сумма округлённых дневных налогов может отличаться и не используется для диапазона. Отрицательный сохранённый налог SKU не обнуляется; агрегатные ограничения действующей методики сохраняются.

День без операций считается подтверждённым пустым только через сохранённое coverage и вход `empty_week` со ссылкой на подтверждающий job; пустой список операций не является доказательством покрытия.

В совместимой дневной публикации все участвующие поколения имеют одинаковые parser/result method UUID и множество выбранных SKU: это условие переноса прежних дней в publication guard. Reader подтверждает этот инвариант по всей выбранной карте; смешанный scope или несовместимые методики — `drilldown_publication_incompatible`, без объединения товаров или новых правил совместимости. Изменение текущего выбора запускает перерасчёт, но историческая публикация сохраняет прежний scope. Разные налоговые настройки внутри совместимой методики читаются по точным фактам и их сохранённым датам.

Текущий builder переносит причины и качество недельного расчёта на дни, а причины сохраняются с областью `store`. Наличие даты у причины не доказывает независимую диагностику этого дня или SKU. Reader сохраняет происхождение причины и не объявляет остальные товары/дни полными без отдельного основания.

## 5. Категории и пользовательские названия

Все категории показываются с исходным знаком. Расходная метрика может менять знак для подписи «расход», но хранит и исходную знаковую сумму. Обратные операции остаются рядом с начислениями.

| Группа | Сохранённые category codes |
|---|---|
| Выручка и финансовые возвраты | `revenue`, `revenue_return` |
| Расходы и корректировки WB | `acquiring`, `logistics`, `storage`, `acceptance`, `penalty`, `deduction`, `commission_adjustment`, `other_adjustment`, `promotion`, `pickup_reward`, `wb_reward_without_vat`, `wb_reward_vat` |
| Обратные расходы и точная коррекция WB | `return_wb_expense_reversal`, `wb_row_rounding_adjustment`; самостоятельные подкатегории, без выдуманного перераспределения по исходным статьям |
| Себестоимость вариантов | `cost_of_goods` (продажа и возврат по цепочке evidence) |
| Дополнительные расходы | `packaging`, `software_services`, `external_promotion`, `agency_services`, `other_external` |
| Налог | `estimated_usn_tax` legacy либо агрегат `daily_tax_range` точных фактов |

Строки `store` показываются отдельно с теми же категориями. Они включаются в итог лишь согласно методике публикации; не распределяются между SKU. Неизвестная категория не исчезает и не получает выдуманную статью: сохраняются code, сумма, причина неподдерживаемого представления, доступные источники. Неизвестная классификация не даёт назвать результат полным.

Обзор сейчас считает `wbExpenses` как все расходы кроме выручки и себестоимости, включая внешние расходы. P0.5 раскрывает эту существующую метрику с её текущим составом, а в карточке отдельно подписывает собственно WB и дополнительные расходы. Сверяется их знаковая сумма; значение обзора нельзя незаметно заменить одной группой WB. «К перечислению» раскрывается существующим составом `WB_TRANSFER_CATEGORIES`; это не остаток денежных средств и не чистая прибыль.

## 6. Контрольные сверки

Сверка воспроизводит сохранённые вклады и действующий агрегатор; новых формул расчёта нет. Обязательные проверки:

1. Для каждой обычной persisted строки сумма всех `contributionAmount` evidence равна `amountSigned` с точностью 4 знака. Неполная страница не участвует как полный набор. Для налогового агрегата проверяются точные факты, их база, ставки/числители и действующее округление; сумму базы нельзя сравнивать с итогом налога.
2. Сумма строк выбранных SKU без налога равна `selectedProductsResultBeforeTax`; сумма включённых строк магазина без налога — `storeLevelResultBeforeTax`. Их включение определяется методикой, а общий результат равен `availableResultBeforeTax`, как проверяет `buildFinancialPeriodOverview`.
3. При пригодном включённом налоге сумма налоговых вкладов SKU со знаком равна `-estimatedUsnTax`; доступный результат после налога равен результату до налога минус опубликованный налог. При непригодном налоге значения после налога и налоговый вклад недоступны, а справка не прибавляется в итог.
4. Контроль выполняется для полного scope и всех вкладов независимо от поиска/пагинации. Общие строки учитываются один раз. SKU отсутствующего в scope нельзя добавить по каталогу.
5. Метрики карточки и списка равны для одного контекста. Состав метрик обзора совпадает с `buildFinancialPeriodOverview`, включая знак возвратов, коррекции и текущее включение внешних расходов.

`reconciliation`: `status: matched / unavailable / mismatch`, `checks` с кодом, ожидаемой и прочитанной суммой, областью проверки и причиной. `matched` означает доказанную сверку доступных величин, а не полную финансовую прибыль. Неполнота расчёта может сочетаться с `matched` доступной части. Нехватка evidence не обнуляет сохранённую сумму и не переписывает quality публикации.

При `mismatch` либо отсутствии обязательной frozen-связи affected группа/источник получает недоступность доказательства; ответ не помечается проверенной расшифровкой. Опубликованная сумма остаётся видимой с явной причиной, запрещено исправлять её текущими входами или увеличивать допуск UI. Сверка денежных строк точная; специальные допуски источников применяются только там, где уже определены расчётной методикой, с указанием правила.

## 7. Отказы и защита источников

Reader сначала проверяет membership, роль чтения, магазин, публикацию, диапазон и принадлежность SKU scope; затем проверяет каждую строку и источник. SQL выполняется с RLS обычной ролью PostgreSQL. Проверка UUID в браузере не заменяет проверку всей цепочки `business → store → publication → day/period → line/fact → evidence → source` на сервере. Viewer разрешено читать; изменение входов остаётся отдельной операцией существующих форм.

| Случай | Планируемый внешний ответ |
|---|---|
| Нет сессии | Существующая обработка авторизации; данные не возвращаются |
| Невалидная дата/UUID, обратный диапазон, limit или cursor | `400 drilldown_invalid_request` |
| Чужой/несуществующий магазин, публикация, SKU, строка, источник; SKU вне scope; публикация другого магазина | Одинаковый `404 drilldown_not_found`, без подтверждения существования чужого ID |
| Cursor относится к другой публикации, группе или фильтру | `400 drilldown_cursor_context_mismatch` |
| У доступной публикации нет точного покрытия периода | Контекст `quality: unavailable`, суммы `null`, причина `drilldown_period_unavailable` вместе с исходными coverage reasons; нет fallback |
| Нет поддерживаемого адаптера старого источника/методики | `evidenceStatus: unavailable`, `drilldown_source_unsupported`; поддерживаемые независимые суммы остаются видны |
| Несовместимые method UUID или разные выбранные SKU в карте дневной публикации | `quality: unavailable`, `drilldown_publication_incompatible`, без смешанного итога |
| Нет обязательного frozen ID/link либо источник принадлежит другой normalization | Источник не выдаётся; `drilldown_frozen_source_missing` для доступной собственной строки. Чужой прямой source ID по-прежнему даёт 404 |
| Не сходятся сохранённые деньги/evidence | `reconciliation: mismatch`, `drilldown_reconciliation_mismatch`, affected детализация недоступна; сохранённая сумма не меняется |

Коды `drilldown_*` — новые коды read-контракта; они не записываются вместо причин финансового расчёта. Внешний ответ не содержит SQL, путей хранилища и сырого текста внутренних ошибок.

Raw WB не возвращается целиком. Первоначальный разрешённый список: `reportId`, `rrdId`, `nmId`, `docTypeName`, `sellerOperName`, `quantity`, `dateFrom`, `dateTo`, `currency`; денежные значения берутся из проверенного компонента/вклада. Отсутствующие поля не восстанавливаются догадками. Типы и длина контролируются; ID не теряют точность через JS Number. Свободный текст экранируется в HTML. `srid` используется сервером для связей, в первоначальный raw-ответ не включается. Токены, персональные поля, реквизиты покупателя и пути файлов запрещены. `imageUrl` допускается только как безопасный URL по существующим правилам каталога.

## 8. Основание контракта и следующий срез

Проверенные точки текущей реализации:

- [Чтение финансового результата](../app/modules/calculation/calculation.repository.mjs): `loadPublishedPeriodEnvelopes`, `getPublishedFinancialPeriod`, `getPublishedFinancialPeriodPair`, `aggregateDailyPublicationPeriod`. Обзорные методы выбирают текущую публикацию; [reader расшифровки](../app/modules/calculation/drilldown.repository.mjs) читает переданный immutable ID в `REPEATABLE READ READ ONLY`, [reader evidence](../app/modules/calculation/drilldown-evidence.repository.mjs) проверяет точные источники.
- [Дневной агрегатор](../app/modules/calculation/daily-generation.mjs): `aggregateDailyFinancialGeneration`; [сохранение поколения](../app/modules/calculation/daily-generation.repository.mjs) и [публикация](../app/modules/calculation/daily-publication.repository.mjs).
- [Проверки обзора](../app/modules/overview/financial-overview.mjs): `buildFinancialPeriodOverview`, `normalizeTax`; [ситуации](../app/modules/overview/situations.mjs): `product_loss` до налога, знаковое сальдо `penalty`, отключённое `return_growth`.
- [Точные frozen WB inputs](../db/migrations/058_exact_wb_row_evidence_input.sql) и последующие guards дневной модели. Наличие guards записи не заменяет проверку принадлежности при чтении.

Совместимые legacy period envelopes и опубликованные дневные поколения поддерживаются. Legacy без сохранённых period envelopes возвращается как `unavailable` с `drilldown_source_unsupported`, без нового расчёта справочного налога и fallback. Миграция не потребовалась: используются существующие frozen-связи, PK и индексы дочерних доказательств. Код не вызывает WB и не ставит задания при чтении.

HTTP: GET `/sku`, `/sku/card` (`productId`), `/sku/sources` (`groupKey` и `productId` либо `scope=store`). Все переходы передают `storeId`, `publicationSource`, `publicationId`, `periodStart`, `periodEnd`. Без публикации только вход в список разрешает текущий результат один раз и перенаправляет на URL с immutable-контекстом; неполный explicit-контекст не заменяется текущим. Поиск/сортировка сбрасывают cursor; `listCursor` хранит страницу возврата отдельно от cursor источников, `taxBasis=1` открывает налоговую базу. Ответы защищены сессией и `Cache-Control: no-store`.

Возврат на `/overview` с publication-контекстом показывает те же сохранённые проверенные суммы через `frozenFinancialOverview`; непригодный налог остаётся null. Сравнения и ситуации другой публикации не подставляются. Текущий обзор открывается явно; финансовый polling и browser localStorage не переписывают frozen-ссылки. При смене магазина публикация и товар сбрасываются, период сохраняется.

Подтверждённые источники получают читаемые размер, цвет и штрихкоды своего варианта. Эти метаданные могут быть текущими или историческими; они не меняют frozen-суммы, область расчёта и доказательства. Raw целиком не публикуется.
