# Marketplace Control: инструкции агентам

## Порядок работы и контекст

- Доводи запрос до проверенного результата самостоятельно; уточняй только требования, без которых нельзя безопасно продолжить. «Только обсуждаем» и «ничего не создавай» запрещают правки.
- Перед изменением проверь `git status`, применимые инструкции и связанный код. Не перезаписывай чужую работу.
- Начинай с карты ниже, `rg` и нужных функций/разделов. Расширяй поиск по зависимостям; не перечитывай весь проект и уже доступные инструкции без причины.
- `README.md` — обзор/запуск, `package.json` и `db/package.json` — команды/зависимости. Проверяй при первом знакомстве или изменении среды; остальные документы читай по задаче.
- Большие словари, миграции, lock-файлы, логи, `work/` и архивы читай выборочно. Ограничивай вывод длинных строк. Успешные проверки резюмируй; ошибки показывай с нужным контекстом.
- Делай минимальный законченный patch в существующем стиле. Без несвязанного рефакторинга, массового форматирования, лишних зависимостей, дублирования и временного кода/TODO вместо реализации.
- Перед изменением интерфейса найди и обнови вызовы; сохраняй совместимость, если запрос не требует обратного. Исправляй первопричину, проверяй соседние сценарии, добавляй подходящие тесты новых функций и регрессий.
- Обновляй документацию при изменении поведения, интерфейсов, конфигурации или запуска. Не расширяй продуктовый scope самостоятельно.

## Оркестрация

- Основная задача определяет scope, координирует агентов, интегрирует результат, выполняет итоговые проверки, коммит и push.
- Для нетривиальных задач оцени независимые части и используй параллельных `mc_explorer` (исследование), `mc_implementer` (реализация), `mc_reviewer` (ревью). Это задачи нескольких подсистем, архитектуры, БД, авторизации, денег, внешних API и безопасности.
- Для простой локальной задачи исследователь/исполнитель необязательны. Делегируй конкретную самостоятельную часть; полный цикл ролей не запускай автоматически.
- До трёх субагентов и до двух пишущих агентов одновременно, включая основного. Запись параллельно — только в непересекающиеся файлы; общий файл или изменение общего интерфейса обрабатываются последовательно.
- Задание агенту: результат, исключительные пути владения, ограничения, нужный контекст и проверки. Запрети менять другие пути; предупреди об общем checkout и чужих правках. Не передавай лишнюю историю.
- Субагенты не делают `git add/commit/push`, не переключают ветки, не публикуют/развёртывают и не расширяют scope. Незнакомые правки в своих файлах, конфликт или выход за владение — остановка записи и блокер оркестратору.
- Отчёт: результат, пути/символы, проверки, риски/блокеры; без копий кода и полных логов. Повторяй исследование только при изменении кода, противоречиях или пробелах.
- Дождись исполнителей и проверь итоговый diff и фактический результат. Отчёт агента не заменяет проверку интеграции.
- Перед коммитом нужен независимый `mc_reviewer`, кроме документации (включая текстовые инструкции) и простых визуальных правок без изменения поведения, доступа, обработки/отправки форм и финансовых данных. Смешанный diff — по наиболее строгой категории; при сомнении проведи ревью.
- БД, аутентификация, финансовые расчёты, внешние API и безопасность требуют усиленного независимого ревью, полного подходящего набора тестов и VM. Исправь подтверждённые замечания до коммита.
- Профили — `.codex/agents/`; детали — `outputs/ai-orchestrator.md` (читай при изменении оркестрации).

## Проверки

- Сначала целевые тесты, затем применимые общие проверки. Команды: `node --test <путь-к-тесту>`, `npm test`, `npm --prefix db test`. Отдельных lint/typecheck/build scripts сейчас нет.
- PostgreSQL-интеграция P0.2/P0.3 и отдельная тестовая БД описаны в `db/README.md`. Проверка схемы также генерирует словарь БД: проверяй его diff.
- Для схемы БД, расчётов и целостности — полный набор тестов приложения и БД. Не повторяй успешные тяжёлые проверки без влияющих изменений, ошибок или нерешённых рисков.
- Итоговые тесты/развёртывания — на VM `marketplacecontrol`, напрямую, без Docker. Локальные прогоны вспомогательные; Docker-файлы сохраняй, Docker Desktop не используй.
- Только документация и конфигурация Codex без кода, схемы или среды приложения: достаточно локальной статической проверки. Визуальное исключение от reviewer не отменяет VM.
- Исправляй вызванные правками ошибки и повторяй нужные проверки. Не выдавай незапущенные проверки за успешные; сообщай ограничения.

## Безопасность и сохранение

- Все новые макеты сохраняй в `outputs/design/Новый дизайн/`: понятные русские папки страниц, вложенность по переходам и группам действий. Варианты внутри страницы — `ПК-светлая-vN.png`, `ПК-тёмная-vN.png`, `Мобильная-светлая-vN.png`, `Мобильная-тёмная-vN.png`. Карту обновляй в `outputs/design/Новый дизайн/README.txt`; прежние одобренные макеты в `Makets` сохраняй как историю.
- Не выводи секреты и не коммить credentials, токены/ключи, персональные выгрузки WB, локальные БД, зависимости и временные файлы. Рабочие материалы — `work/`, документы — `outputs/`. Сохраняй изоляцию данных и контроль доступа.
- После завершённого изменения и проверок — один содержательный коммит по запросу и `git push origin main`. Постоянное разрешение пользователя включает документы; повторное согласование не нужно.
- Только оркестратор проверяет staging и делает коммит/push. Включай лишь изменения задачи, без force push. При конфликте/отсутствии доступа сохрани локальный результат и сообщи, что не отправлено.
- На VM приложение и PostgreSQL работают напрямую; проверенные обновления `main` поступают автоматически из GitHub.
- Итог: кратко сделано, проверено, короткий commit ID; ограничения — если остались. Без повторения хода работы и полного списка файлов без необходимости.

## graphify

This project has a knowledge graph at graphify-out/ with god nodes, community structure, and cross-file relationships.

When the user types `/graphify`, use the installed graphify skill or instructions before doing anything else.

Rules:
- For codebase questions, first run `graphify query "<question>"` when graphify-out/graph.json exists. Use `graphify path "<A>" "<B>"` for relationships and `graphify explain "<concept>"` for focused concepts. These return a scoped subgraph, usually much smaller than GRAPH_REPORT.md or raw grep output.
- Dirty graphify-out/ files are expected after hooks or incremental updates; dirty graph files are not a reason to skip graphify. Only skip graphify if the task is about stale or incorrect graph output, or the user explicitly says not to use it.
- If graphify-out/wiki/index.md exists, use it for broad navigation instead of raw source browsing.
- Read graphify-out/GRAPH_REPORT.md only for broad architecture review or when query/path/explain do not surface enough context.
- After modifying code, run `graphify update .` to keep the graph current (AST-only, no API cost).
