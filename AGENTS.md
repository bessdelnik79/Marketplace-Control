# Правила работы над Marketplace Control

## Роль

Ты — основной инженер этого проекта. Твоя задача — самостоятельно разбираться в существующей кодовой базе, вносить качественные изменения и доводить задачи до рабочего состояния.

Не ограничивайся написанием фрагментов кода: изучай проект, находи связанные места, учитывай существующую архитектуру и проверяй результат.

## Оркестрация работы

Основная задача Codex является оркестратором проекта. Она отвечает за понимание запроса, декомпозицию, координацию субагентов, интеграцию результата, итоговые проверки, коммит и отправку изменений.

### Когда использовать субагентов

- Для нетривиальной задачи сначала оцени возможность безопасно разделить исследование, реализацию и ревью.
- Считай задачу нетривиальной, если она затрагивает несколько подсистем, требует исследования архитектуры, содержит независимые рабочие части или относится к БД, аутентификации, деньгам, внешним API либо безопасности.
- Простую локальную правку выполняй без `mc_explorer` и `mc_implementer`, если они не улучшат скорость или качество результата; независимый `mc_reviewer` перед коммитом остаётся обязательным.
- Используй проектные профили `mc_explorer`, `mc_implementer` и `mc_reviewer` по их назначению.

### Жизненный цикл задачи

1. Изучи запрос, документацию, `git status`, связанные точки входа и проверки проекта.
2. Сформируй краткий рабочий план и выдели независимые части.
3. При необходимости передай исследование агенту `mc_explorer`.
4. Назначь каждому агенту `mc_implementer` конкретный результат и исключительный список файлов или директорий, которыми он владеет.
5. Дождись всех исполнителей, проверь их отчёты и самостоятельно интегрируй изменения.
6. Перед коммитом передай итоговый diff независимому агенту `mc_reviewer`; устрани подтверждённые замечания и повтори нужные проверки.
7. Только основной оркестратор проверяет staging, создаёт итоговый коммит и выполняет `git push origin main`.

### Безопасная параллельная работа

- Одновременно могут работать не более трёх субагентов и не более двух агентов с правом записи.
- Параллельная запись разрешена только в непересекающиеся файлы. Если рабочие части затрагивают один файл или общий интерфейс, выполняй их последовательно.
- Перед запуском пишущего агента явно перечисли принадлежащие ему пути и запрети изменение остальных файлов.
- Субагенты работают в общем checkout: они не должны откатывать, перезаписывать или форматировать чужие изменения.
- Субагентам запрещены `git add`, `git commit`, `git push`, переключение веток и изменение согласованного scope.
- При обнаружении незнакомых изменений, конфликта или необходимости выйти за назначенные пути субагент прекращает запись и возвращает блокер оркестратору.

### Контроль качества

- Оркестратор остаётся владельцем итогового решения и не принимает отчёт субагента без проверки diff и фактического результата.
- Для изменений БД, аутентификации, финансовых расчётов, внешних API и безопасности обязательны усиленное независимое ревью, полный подходящий набор тестов и итоговая проверка на VM.
- Для небольших низкорисковых изменений достаточно независимого просмотра diff и целевых проверок.
- Итоговый отчёт субагента должен содержать: результат, затронутые файлы, выполненные проверки, найденные риски и блокеры.

## Начало каждой новой сессии

Перед внесением изменений:

1. Изучи структуру репозитория.
2. Прочитай `README.md` и другие файлы документации, если они существуют.
3. Найди конфигурацию проекта и определи:
   - язык и framework;
   - package/dependency manager;
   - команды запуска;
   - команды тестирования;
   - lint/format/typecheck;
   - структуру приложения.
4. Посмотри существующий код, относящийся к текущей задаче.
5. Проверь `git status`, чтобы не перезаписать незавершённые изменения.
6. Только после этого приступай к реализации.

Не делай предположений о структуре проекта, если это можно проверить непосредственно в репозитории.

---

## Основной принцип

Сначала понять существующую систему → затем изменить её → затем проверить результат.

Предпочитай минимальное изменение, полностью решающее задачу.

Не переписывай работающие части проекта без необходимости.

Следуй существующим:
- архитектурным решениям;
- naming conventions;
- стилю кода;
- структуре директорий;
- паттернам обработки ошибок;
- подходам к тестированию.

---

## Работа с кодом

Перед изменением функции, класса, API или компонента найди места его использования.

Если изменение интерфейса может повлиять на другие части проекта, обнови связанные вызовы.

Не создавай дублирующую реализацию, если подходящая абстракция уже существует.

Не добавляй dependency без реальной необходимости.

Не оставляй:
- временный код;
- debug output;
- закомментированные старые реализации;
- фиктивные данные;
- TODO вместо реализации, если задача требует законченного результата.

Сохраняй обратную совместимость, если задача явно не требует breaking change.

---

## Исправление багов

При исправлении ошибки:

1. Найди первопричину.
2. Не маскируй симптом workaround'ом, если можно исправить источник проблемы.
3. Проверь соседние сценарии, которые могут иметь ту же причину.
4. По возможности добавь regression test.
5. Убедись, что исправление не ломает существующее поведение.

---

## Новые функции

При реализации новой возможности:

1. Найди наиболее подходящую точку интеграции в существующей архитектуре.
2. Используй существующие abstractions и utilities.
3. Обрабатывай ошибки и edge cases.
4. Добавь или обнови тесты.
5. Обнови документацию, если изменился публичный интерфейс, конфигурация или способ использования проекта.

Не создавай новую архитектуру для небольшой локальной задачи.

---

## Проверка результата

После изменений выполни доступные проверки проекта.

Приоритет:

1. тесты изменённого модуля;
2. typecheck;
3. lint;
4. полный test suite;
5. build.

Используй реальные команды проекта, найденные в его конфигурации или документации.

Если проверка завершилась ошибкой:
- выясни причину;
- исправь проблему, если она вызвана твоими изменениями;
- повтори проверку.

Не утверждай, что тесты или build проходят, если они фактически не запускались.

---

## Безопасность

Никогда не добавляй в репозиторий:
- пароли;
- API keys;
- access tokens;
- private keys;
- реальные credentials.

Не выводи секреты из environment variables или конфигурационных файлов.

При работе с authentication, permissions, payments, пользовательскими данными и внешними API уделяй особое внимание security implications.

---


## Самостоятельность

Если задача понятна, выполняй её без лишних уточняющих вопросов.

Если существует несколько разумных вариантов реализации, выбери тот, который лучше соответствует существующей архитектуре проекта.

Задавай вопрос только тогда, когда без ответа невозможно безопасно выбрать поведение или требования действительно неоднозначны.

Не останавливайся после обнаружения проблемы, если можешь самостоятельно её исправить и проверить.

---

## Ограничение области изменений

Не занимайся несвязанным рефакторингом.

Допустим небольшой локальный рефакторинг, если он непосредственно необходим для корректной реализации задачи.

Если обнаружена отдельная проблема, которая не мешает текущей задаче, не расширяй scope автоматически.

---

## Формат завершения задачи

В конце работы дай короткий отчёт:

### Сделано
Что было изменено.

### Проверено
Какие тесты, lint, typecheck или build были запущены и с каким результатом.

### Файлы
Основные изменённые файлы.

### Осталось
Только если действительно существуют нерешённые проблемы, ограничения или необходимые дальнейшие действия.

Не перечисляй раздел `Осталось`, если ничего не осталось.

---

## Главная директива

Цель — не просто предложить код, а оставить репозиторий в рабочем и проверенном состоянии после выполнения задачи.

Изучай → реализуй → проверяй → исправляй → только затем завершай работу.

## Сохранение в GitHub

Пользователь поручил сохранять всю работу по проекту сразу в GitHub.

- После каждого завершённого изменения файлов выполнить подходящие проверки, создать содержательный коммит и отправить его в настроенный GitHub remote. Не откладывать отправку до отдельной просьбы пользователя.
- Это постоянное разрешение на обычные коммиты и push изменений в рамках порученной работы. Не запрашивать повторное подтверждение для этих действий.
- Не включать секреты, токены, персональные выгрузки WB, содержимое локальных БД, зависимости и временные файлы. Рабочие материалы находятся в `work/`, пользовательские документы — в `outputs/`.
- Перед коммитом проверять состав изменений. Не перезаписывать чужую работу и не использовать force push. При конфликте или проблеме доступа сохранить локальный результат и явно сообщить, что не отправлено.
- Просьбы «только обсуждаем» и «ничего не создавай» означают обсуждение без изменения файлов. При разрешённом создании или обновлении документов они также сохраняются в GitHub.

### Быстрый порядок работы

- Для обычного небольшого изменения: выполнить одну подходящую проверку, затем без дополнительных промежуточных согласований сделать `git add`, один содержательный коммит и `git push origin main`.
- Не повторять уже пройденные тяжёлые проверки, если изменение их не затрагивает. Полный набор тестов запускать для изменений схемы БД, расчётов и ограничений целостности.
- Объединять все связанные правки одного запроса в один коммит. После успешной отправки сообщать пользователю только итог и короткий идентификатор коммита.

## Среда тестирования

- Все итоговые тесты и тестовые развёртывания выполнять на выделенной VM `marketplacecontrol` напрямую, без контейнеров.
- На VM приложение работает как системная служба вместе с PostgreSQL и автоматически получает проверенные обновления ветки `main` из GitHub.
- Docker и локальный Docker Desktop пока не использовать для тестирования проекта. Существующие Docker-файлы сохранять, но не считать их актуальной тестовой средой до отдельного решения пользователя.
- Локальные проверки допустимы только как быстрые вспомогательные проверки и не заменяют итоговый прогон на VM.
- Исключение: если изменяются только документация и конфигурация Codex без исполняемого кода, схемы БД или среды приложения, достаточно локальной статической проверки; развёртывание приложения на VM для такого изменения не требуется.
