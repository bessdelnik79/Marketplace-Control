Готовые транзакционные миграции PostgreSQL и проверки модели. На VM работает подключение WB с зашифрованным хранением токена, загрузка каталога и детализации финансовых отчётов; обработчик платежей ещё не реализован.

Миграция [073 — хранение тарифных профилей](migrations/073_tariff_profile_foundation.sql) добавляет отдельные профили, их магазины и товары и указатель оформленного профиля. Она сохраняет старый реестр выбора и действующие правила доступа; переключение потребителей и автоматическое окончание тарифа выполняются следующими этапами [плана](../outputs/tariff-lifecycle-plan.md). Снимок текущего платного выбора переносится отдельно, недоказанный первоначальный бесплатный набор не угадывается. Перед включением переходов нужна повторная сверка изменений старого выбора после миграции.

Профильная проверка на одноразовом PostgreSQL проверяет регистрацию, перенос существующих данных и межкабинетные ограничения:

```sh

```

## Применение

Из корня проекта, к **новой пустой** базе PostgreSQL:

```sh
createdb marketplace_control
psql --dbname=marketplace_control --set=ON_ERROR_STOP=1 --file=db/migrations/001_initial.sql
```

Команды предполагают уже установленный PostgreSQL и настроенную аутентификацию. Исходная миграция создаёт схему `mc`; следующие миграции добавляют регистрацию, защиту, первый вход и зашифрованные секреты интеграции. Каждая выполняется в транзакции. Автоматического удаления схемы и разрушительной обратной миграции нет.

Файлы из `/docker-entrypoint-initdb.d` выполняются PostgreSQL только при создании пустого тома. Последующие миграции применяет мигратор приложения до запуска веб-сервера.

Схема проверяется на PostgreSQL 17.5 внутри PGlite 0.3.14. Итоговая среда проекта — выделенная VM с PostgreSQL и приложением без Docker; PGlite остаётся быстрой изолированной проверкой миграций и ограничений.

Прикладные методы P0.2 дополнительно проверяются на настоящем PostgreSQL в отдельной одноразовой базе, имя которой обязательно содержит `test`:

Счётчики страницы ситуации (товар/точный период, принятые оперативные snapshots, подтверждённые нули, неполные дни, сохранённый fallback, чужой tenant и недоступный товар):

```sh
P04_INTEGRATION_DATABASE_URL=postgresql:///marketplace_control_situation_counts_test node db/tests/situation-counts.integration.mjs
```

Он фиксирует выбор товаров, нормализацию отчёта, себестоимость, точный результат по доступным данным, причины неполноты и идемпотентную текущую публикацию. Тест также отказывается работать с базой, в имени которой нет `test`.

Тот же сценарий содержит интеграцию readers P0.5: список SKU, карточку, страницы денежных вкладов и налоговой базы. Он читает сохранённую legacy-публикацию и дневную публикацию из нескольких поколений обычной ролью PostgreSQL (`NOSUPERUSER`, `NOBYPASSRLS`) от имени viewer. Проверяются настоящие чужие business/store/product/publication/line IDs, другая нормализация той же версии отчёта, смена текущей публикации между кликами и несовместимая методика перенесённого поколения. HTTP acceptance (`tests/p05-http.acceptance.mjs`) проходит с настоящей подтверждённой сессией viewer: обзор → SKU → себестоимость → источник → прежний обзор, отдельно legacy налоговую базу; jobs и версии WB не меняются. Для adversarial fixture bootstrap-роль временно изменяет только одноразовые snapshots и восстанавливает их; рабочую БД использовать нельзя.

Для отдельно разрешённой приёмки **уже сохранённых данных** используется `tests/p05-live.acceptance.mjs`. Он не создаёт финансовые fixtures и не меняет входы, публикации, ассортимент или подключения. `DATABASE_URL` должен задавать обычную роль приложения без SUPERUSER/BYPASSRLS; `P05_LIVE_CONTEXT_PATH` указывает приватный JSON с `userId`, `businessId` и `profiles`, каждый из которых содержит `input` с `storeId`, `publicationSource`, `publicationId`, `periodStart`, `periodEnd`. Файл контекста и результаты с данными кабинета хранятся вне Git в `work/` с ограниченным доступом. Автоматического выбора чужого кабинета нет.

```sh
P05_LIVE_CONTEXT_PATH=work/p05-live-profiles.json P05_LIVE_BASE_URL=http://127.0.0.1:3000 node db/tests/p05-live.acceptance.mjs
```

Проверка проходит все страницы вкладов, сверку SKU и общих строк, правила ситуаций, налоговую базу и HTTP-ссылки до источников и обратно. `P05_LIVE_PAGE_LIMIT` задаёт размер reader-страницы 1–100 (по умолчанию 25); для проверки курсоров использован лимит два. Необязательный `expectNewPublication: true` в профиле требует сохранённую старую публикацию с явной ссылкой к более новой. Конфигурация авторизации (`NODE_ENV`, `EMAIL_VERIFICATION_REQUIRED`) должна совпадать с проверяемым приложением.

HTTP использует временную сессию указанного существующего пользователя с удалением в `finally`; адрес ограничен loopback. Кроме живого приложения, те же переходы проходят через временный localhost-сервер с реальными финансовыми route factories и заблокированным внешним fetch; он не запускает миграции или workers. Его operational-read пустой, область доказательства — финансовые GET. Сервер закрывается до удаления сессии. Остальные операции БД — чтение. Вывод содержит счётчики и причины неполноты без raw, credentials, идентификаторов аккаунта и финансовых сумм. Количество jobs/версий отчётов проверяется отдельно от временной auth-сессии. Этот сценарий требует живого приложения и не входит в автоматический `npm test`.

## Контракт серверного доступа

Для тестирования на VM доступен режим `EMAIL_VERIFICATION_REQUIRED=false` вне production: регистрация создаёт сессию без письма, но не выставляет `email_verified_at`. После возврата обязательной проверки такие сессии снова не дают доступ. Миграция `004_password_identity_lookup.sql` разрешает доверенному серверу поиск только запрошенной password-идентичности по транзакционному `app.auth_email`; пользовательский и бизнес-контексты сервер устанавливает из проверенных идентичностей и сессий, а не из переданного браузером ID.

Регистрация по паролю считается завершённой только после одноразового email-кода. Яндекс ID создаёт подтверждённую внешнюю идентичность через OAuth. До подтверждения идентичности сессия не даёт доступ к защищённым маршрутам. Следующий уровень допуска к импорту и расчётам должен проверять активное подключение кабинета WB. Телефонная проверка отложена до появления подтверждённых риск-сценариев и не является обязательной для обычной регистрации MVP.

1. Сервер проверяет аутентификацию и членство пользователя в бизнесе. Значения `app.user_id` и `app.business_id` не принимаются от браузера как доказательство доступа.
2. На каждый запрос сервер открывает транзакцию, выставляет оба контекста через `set_config(..., true)`, проверяет выбранный магазин и выполняет запросы с его `store_id`.
3. Прикладные роли не являются владельцем БД, суперпользователем и не имеют `BYPASSRLS`. Миграция не выдаёт прав `PUBLIC`; роли и точечные разрешения создаются при внедрении серверного приложения.
4. Пользователям не предоставляется SQL-доступ. Исходные отчёты, платежные таблицы, подписки и задания доступны только доверенным серверным компонентам. Роль веб-приложения не должна получать право менять подписку или условия тарифов.
5. Каталог нужен для первого выбора. После подтверждения товарная аналитика читается через `mc.selected_products` и `mc.current_daily_results`, с фильтром текущего магазина. Эти представления учитывают активность магазина и подписки. Они не заменяют проверку доступа для скачивания файлов и отдельных API-методов.
6. Для первого подтверждения вызывается `mc.confirm_product_selection(store_id, catalog_document_id, product_ids)`, для последующего добора — `mc.add_products_to_selection(store_id, product_ids)`. Обе функции проверяют текущего пользователя и бизнес, целостность списка, принадлежность товаров и лимит тарифа. Непосредственная запись в подтверждённый набор заблокирована.
7. Для фоновых задач также устанавливается бизнес-контекст. Системный диспетчер очереди и обработчик входящих платежных событий требуют отдельных узких привилегий, а не обхода RLS во всём приложении.

Пример контекста в транзакции (значения передаются параметрами драйвера):

```sql
BEGIN;
SELECT set_config('app.business_id', :business_id, true);
SELECT set_config('app.user_id', :user_id, true);
SELECT mc.confirm_product_selection(:store_id, :catalog_document_id, :product_ids);
COMMIT;
```

Двоеточия здесь обозначают параметры приложения, а не готовую команду psql.

## Запись и версии

- Себестоимость: массовый импорт создаёт `source_documents`, `import_batches` и неизменяемые `import_rows`, затем создаёт `variant_costs` для даты начала действия, `cost_versions` и переключает `current_version_id` в одной транзакции. При любой ошибке файл получает статус `failed`, а значения не применяются. При исправлении суммы на ту же дату создаётся новая версия; одинаковая сумма пропускается. Для новой даты создаётся новая запись `variant_costs`. Нельзя менять дату уже сохранённой записи; исправление ошибочной даты требует отдельного явно спроектированного сценария. Пользовательский контракт описан в [документе импорта](../outputs/cost-import.md).
- Расход: создать `expenses`, затем `expense_versions` и переключить указатель в одной транзакции. `product_id IS NULL` означает общий расход магазина; непустой `product_id` обязан ссылаться на выбранный товар того же магазина. В файлах используется устойчивый ID расхода; повтор исходного файла без ID дополнительно дедуплицируется по контрольной сумме и номеру строки.
- Налоговая настройка: `tax_settings` задаёт дату начала действия на уровне бизнеса, `tax_setting_versions` хранит неизменяемые исправления режима, точной ставки УСН и независимого статуса НДС. Отсутствие настройки не означает нулевой налог. В пилоте исполняемой будет только будущая методика УСН «Доходы»; остальные режимы не рассчитываются приблизительно.
- Отчёт: загрузить полный исходник, создать версию `received`, записать строки, нормализовать и сверить, перевести в `validated`, затем `accepted`. Только после этого переключать указатель отчёта. Нельзя добавлять строки после начала валидации.
- Расчёт: `calculation_requests` хранит последнее желаемое поколение и frozen snapshot товаров/входов. Каждая попытка создаёт неизменяемый `calculation_run`; строки и доказательства должны сойтись до атомарной публикации под блокировкой магазина. Повтор того же fingerprint не создаёт новую публикацию. `financial-result-v20` использует формулы v19, но сохраняет один exact-range envelope произвольного периода только при непрерывном покрытии frozen-отчётами. Отрицательный налоговый вклад отдельного SKU уменьшает положительный налог остальных товаров; отрицательный итог периода остаётся fail-closed.
- Нормализация `wb_finance_import` отделена от raw-версии отчёта и может повторно обработать тот же checksum новой версией метода. `wb-finance-v11` различает нулевые sentinels, не принимает `srid`/`shkId` за товарную привязку и сохраняет `cashbackDiscount` как справочное поле `loyalty_discount_reference`, уже учтённое в выручке. Известные результативные компоненты строки без реального `nmId`/`sku`/`saName`/`barcode` относятся к scope магазина с сохранением нормализованного знака; неизвестные поля остаются fail-closed. `rebillLogisticCost`, `forPay`, `ppvzSalesCommission` и `loyalty_discount_reference` имеют scope `reconciliation` и в результат не входят; v19/v20 также исключают `vw` и `vwNds` из точной строки транспортного возмещения как справочную часть связки с `rebillLogisticCost`. Исполняемый `financial-result-v19` сохраняет отдельный envelope для каждой недели, включает store-level результат в доступный итог и учитывает отрицательный налоговый вклад SKU; v20 обслуживает exact-range. Старые публикации остаются читаемыми. Связанный возврат восстанавливает себестоимость исходной продажи. Результат не называется чистой прибылью.
- Оперативная воронка хранит зашифрованный raw-ответ отдельно от финансовых исходников. `operational_snapshots` замораживает выбранные товары и дневные метрики, проходит `received → validated → accepted`, после чего период атомарно переключает `current_snapshot_id`. `current_operational_daily_metrics` разрешает перекрывающиеся rolling-окна по самому свежему принятому snapshot для каждого товара и дня. Отсутствующая строка остаётся явным пробелом `partial`/`unavailable`, а не нулём или устаревшим значением.
- `mc.jobs` после миграции 034 хранит durable lifecycle `pending → running → succeeded|failed`. Worker получает задание атомарно через `FOR UPDATE SKIP LOCKED`, подтверждает владение парой `worker_id`/`lease_token`, продлевает lease heartbeat-запросом и может вернуть временную ошибку в `pending` с backoff. Просроченный `running` восстанавливается другим worker; после `max_attempts` становится terminal `failed`. Закрытый `mc.job_dispatch` служит только межтенантным индексом обнаружения: функция блокирует его строку, устанавливает контекст найденного бизнеса и лишь затем меняет защищённую `FORCE RLS` строку `mc.jobs`. Пользовательская постановка выводит бизнес из проверенного tenant-контекста, а worker-функции закрыты от `PUBLIC`.

Runtime-роль worker создаётся инфраструктурой, а не миграцией приложения. Ей нужны только `USAGE` на схему `mc` и `EXECUTE` на `claim_jobs`, `heartbeat_job`, `complete_job`, `fail_job`; права на таблицы, `enqueue_job`, context-функции, `SUPERUSER` и `BYPASSRLS` не выдаются. Владелец этих `SECURITY DEFINER`-функций также не обязан иметь `BYPASSRLS`: ему нужны точечные table grants и `EXECUTE` на `context_business_id()`, чтобы политика `mc.jobs` могла проверить контекст, установленный из закрытого dispatch-индекса. Такой контракт отдельно проверяет `db/tests/jobs.integration.mjs` двумя ролями без входа и без обхода RLS.

## Лимиты и пока открытые решения

Бесплатный тариф назначается новому бизнесу автоматически. Платные версии содержат `price = NULL`: цены не согласованы. Наличие этих записей не означает подключённый эквайринг. Ежемесячный период — начальная конфигурация; ежегодные условия можно добавить новой версией.

Лимит товаров суммарный по бизнесу; один артикул в магазине считается одной единицей независимо от количества вариантов. Приостановленный магазин занимает место, архивный — нет. Его выбранные товары продолжают занимать товарный лимит: архивирование не является способом замены закреплённого ассортимента.

Выбор фиксируется один раз на магазин и допускает от одного товара до доступного остатка лимита. После подтверждения разрешён только контролируемый добор активных товаров через серверную функцию — удаление и замена прежних позиций запрещены. Снижение тарифа ниже сохранённого количества товаров/магазинов отклоняется. При истечении подписки история остаётся, представления аналитики закрывают доступ; автоматический переход на бесплатный тариф пока не задан.

Проверены ограничения и бизнес-сценарии в одном встроенном PostgreSQL. Многопользовательская нагрузка, гонки двух реальных соединений, резервное восстановление, подключение WB и платёжные подписи не тестировались. ## Тарифный цикл (миграции 073–075)

`tariff_profiles` хранит отдельный состав каждого тарифа, `tariff_profile_state` — оформленную активацию. Текущий доступ читает `effective_tariff_context()`, `active_profile_stores`, `active_profile_products`; исторические selections не удаляются. Точный срок проверяется при чтении, суточная задача `expire_due_tariff_subscriptions()` оформляет переход один раз в день. Её индекс и даты проходов закрыты для обычной роли.

`apply_tariff_period()` доступна доверенной административной роли; пользовательский HTTP сохраняет только намерение. Подтверждения идемпотентны по ключу и записываются в неизменяемый аудит. `tariff_scope_token` защищает старые и новые публикации от выдачи результата другого набора. Порядок блокировок: бизнес → магазин/запрос.
