## Применение

Из корня проекта, к **новой пустой** базе PostgreSQL:

```sh
createdb marketplace_control
psql --dbname=marketplace_control --set=ON_ERROR_STOP=1 --file=db/migrations/001_initial.sql
```

Команды предполагают уже установленный PostgreSQL и настроенную аутентификацию. Исходная миграция создаёт схему `mc`; следующие миграции добавляют регистрацию, защиту, первый вход и зашифрованные секреты интеграции. Каждая выполняется в транзакции. Автоматического удаления схемы и разрушительной обратной миграции нет.

Файлы из `/docker-entrypoint-initdb.d` выполняются PostgreSQL только при создании пустого тома. Последующие миграции применяет мигратор приложения до запуска веб-сервера.

Схема проверяется на PostgreSQL 17.5 внутри PGlite 0.3.14. Итоговая среда проекта — выделенная VM с PostgreSQL и приложением без Docker; PGlite остаётся быстрой изолированной проверкой миграций и ограничений.

## Проверки

При доступном npm:

```sh
npm install --prefix db
npm --prefix db test
```

Тест создаёт одноразовую БД в памяти, применяет миграцию, проверяет ограничения и формирует словарь `outputs/database-v1-dictionary.md` из системного каталога PostgreSQL. Тестовые товары, суммы, пользователи и методика не попадают в миграцию или рабочую базу.

Прикладные методы P0.2 дополнительно проверяются на настоящем PostgreSQL в отдельной одноразовой базе, имя которой обязательно содержит `test`:

```sh
P02_INTEGRATION_DATABASE_URL=postgresql:///marketplace_control_p02_test node db/tests/p02-app.integration.mjs
```

Сценарий проверяет ручные версии и аннулирование расходов, повторный и ошибочный импорт, конкурентное исправление, роли и tenant scope, точные налоговые ставки, даты действия и отсутствие молчаливого возврата к прежней ставке после аннулирования. Тест отказывается запускаться без явно заданной безопасной тестовой БД.

Расчёт P0.3 проверяется отдельным сценарием на настоящем PostgreSQL:

```sh
P03_INTEGRATION_DATABASE_URL=postgresql:///marketplace_control_p03_test node db/tests/p03-app.integration.mjs
```

Он фиксирует выбор товаров, нормализацию отчёта, себестоимость, точный результат по доступным данным, причины неполноты и идемпотентную текущую публикацию. Тест также отказывается работать с базой, в имени которой нет `test`.

Хранение оперативных snapshot P0.4 проверяется отдельным сценарием на настоящем PostgreSQL:

```sh
P04_INTEGRATION_DATABASE_URL=postgresql:///marketplace_control_p04_test node db/tests/p04-operational.integration.mjs
```

Сценарий проверяет атомарную публикацию полной и частичной версии, неизменяемую историю, повтор checksum без дубля версии, состояние ошибки, tenant isolation и общий rate-slot Analytics.

В среде без npm можно указать путь к установленному модулю PGlite через переменную `PGLITE_MODULE`. В текущей сессии использовался скачанный в `work/` пакет версии 0.3.14, проверенный по SHA-512 из реестра. Каталог `work/` исключён из Git.

## Контракт серверного доступа

Для тестирования на VM доступен режим `EMAIL_VERIFICATION_REQUIRED=false` вне production: регистрация создаёт сессию без письма, но не выставляет `email_verified_at`. После возврата обязательной проверки такие сессии снова не дают доступ. Миграция `004_password_identity_lookup.sql` разрешает доверенному серверу поиск только запрошенной password-идентичности по транзакционному `app.auth_email`; пользовательский и бизнес-контексты сервер устанавливает из проверенных идентичностей и сессий, а не из переданного браузером ID.

Регистрация по паролю считается завершённой только после одноразового email-кода. Яндекс ID создаёт подтверждённую внешнюю идентичность через OAuth. До подтверждения идентичности сессия не даёт доступ к защищённым маршрутам. Следующий уровень допуска к импорту и расчётам должен проверять активное подключение кабинета WB. Телефонная проверка отложена до появления подтверждённых риск-сценариев и не является обязательной для обычной регистрации MVP.

1. Сервер проверяет аутентификацию и членство пользователя в бизнесе. Значения `app.user_id` и `app.business_id` не принимаются от браузера как доказательство доступа.
2. На каждый запрос сервер открывает транзакцию, выставляет оба контекста через `set_config(..., true)`, проверяет выбранный магазин и выполняет запросы с его `store_id`.
3. Прикладные роли не являются владельцем БД, суперпользователем и не имеют `BYPASSRLS`. Миграция не выдаёт прав `PUBLIC`; роли и точечные разрешения создаются при внедрении серверного приложения.
4. Пользователям не предоставляется SQL-доступ. Исходные отчёты, платежные таблицы, подписки и задания доступны только доверенным серверным компонентам. Роль веб-приложения не должна получать право менять подписку или условия тарифов.
5. Каталог нужен для первого выбора. После подтверждения товарная аналитика читается через `mc.selected_products` и `mc.current_daily_results`, с фильтром текущего магазина. Эти представления учитывают активность магазина и подписки. Они не заменяют проверку доступа для скачивания файлов и отдельных API-методов.
6. Для первого подтверждения вызывается `mc.confirm_product_selection(store_id, catalog_document_id, product_ids)`, для последующего добора — `mc.add_products_to_selection(store_id, product_ids)`. Обе функции проверяют текущего пользователя и бизнес, целостность списка, принадлежность товаров и лимит тарифа. Непосредственная запись в подтверждённый набор заблокирована.
7. Для фоновых задач также устанавливается бизнес-контекст. Системный диспетчер очереди и обработчик входящих платежных событий требуют отдельных узких привилегий, а не обхода RLS во всём приложении.

Пример контекста в транзакции (значения передаются параметрами драйвера):

```sql
BEGIN;
SELECT set_config('app.business_id', :business_id, true);
SELECT set_config('app.user_id', :user_id, true);
SELECT mc.confirm_product_selection(:store_id, :catalog_document_id, :product_ids);
COMMIT;
```

Двоеточия здесь обозначают параметры приложения, а не готовую команду psql.

## Запись и версии

- Себестоимость: массовый импорт создаёт `source_documents`, `import_batches` и неизменяемые `import_rows`, затем создаёт `variant_costs` для даты начала действия, `cost_versions` и переключает `current_version_id` в одной транзакции. При любой ошибке файл получает статус `failed`, а значения не применяются. При исправлении суммы на ту же дату создаётся новая версия; одинаковая сумма пропускается. Для новой даты создаётся новая запись `variant_costs`. Нельзя менять дату уже сохранённой записи; исправление ошибочной даты требует отдельного явно спроектированного сценария. Пользовательский контракт описан в [документе импорта](../outputs/cost-import.md).
- Расход: создать `expenses`, затем `expense_versions` и переключить указатель в одной транзакции. `product_id IS NULL` означает общий расход магазина; непустой `product_id` обязан ссылаться на выбранный товар того же магазина. В файлах используется устойчивый ID расхода; повтор исходного файла без ID дополнительно дедуплицируется по контрольной сумме и номеру строки.
- Налоговая настройка: `tax_settings` задаёт дату начала действия на уровне бизнеса, `tax_setting_versions` хранит неизменяемые исправления режима, точной ставки УСН и независимого статуса НДС. Отсутствие настройки не означает нулевой налог. В пилоте исполняемой будет только будущая методика УСН «Доходы»; остальные режимы не рассчитываются приблизительно.
- Отчёт: загрузить полный исходник, создать версию `received`, записать строки, нормализовать и сверить, перевести в `validated`, затем `accepted`. Только после этого переключать указатель отчёта. Нельзя добавлять строки после начала валидации.
- Расчёт: `calculation_requests` хранит последнее желаемое поколение и frozen snapshot товаров/входов. Каждая попытка создаёт неизменяемый `calculation_run`; строки и доказательства должны сойтись до атомарной публикации под блокировкой магазина. Повтор того же fingerprint не создаёт новую публикацию.
- Нормализация `wb_finance_import` отделена от raw-версии отчёта и может повторно обработать тот же checksum новой версией метода. `wb-finance-v5` различает нулевые sentinels, внутреннее продвижение WB и точные магазинные компоненты ПВЗ без их взаимозачёта. Исполняемый `financial-result-v6` сохраняет отдельный envelope для каждой недели и явный нулевой налог выбранного SKU без продаж только при полном покрытии. Связанный возврат восстанавливает себестоимость исходной продажи; неподтверждённые операции исключаются fail-closed. Результат не называется чистой прибылью.
- Оперативная воронка хранит зашифрованный raw-ответ отдельно от финансовых исходников. `operational_snapshots` замораживает выбранные товары и дневные метрики, проходит `received → validated → accepted`, после чего период атомарно переключает `current_snapshot_id`. `current_operational_daily_metrics` разрешает перекрывающиеся rolling-окна по самому свежему принятому snapshot для каждого товара и дня. Отсутствующая строка остаётся явным пробелом `partial`/`unavailable`, а не нулём или устаревшим значением.

## Лимиты и пока открытые решения

Бесплатный тариф назначается новому бизнесу автоматически. Платные версии содержат `price = NULL`: цены не согласованы. Наличие этих записей не означает подключённый эквайринг. Ежемесячный период — начальная конфигурация; ежегодные условия можно добавить новой версией.

Лимит товаров суммарный по бизнесу; один артикул в магазине считается одной единицей независимо от количества вариантов. Приостановленный магазин занимает место, архивный — нет. Его выбранные товары продолжают занимать товарный лимит: архивирование не является способом замены закреплённого ассортимента.

Выбор фиксируется один раз на магазин и допускает от одного товара до доступного остатка лимита. После подтверждения разрешён только контролируемый добор активных товаров через серверную функцию — удаление и замена прежних позиций запрещены. Снижение тарифа ниже сохранённого количества товаров/магазинов отклоняется. При истечении подписки история остаётся, представления аналитики закрывают доступ; автоматический переход на бесплатный тариф пока не задан.

## Границы проверки

Проверены ограничения и бизнес-сценарии в одном встроенном PostgreSQL. Многопользовательская нагрузка, гонки двух реальных соединений, резервное восстановление, подключение WB и платёжные подписи не тестировались. Лимиты сериализуются блокировкой строки бизнеса; перед production нужен конкурентный интеграционный тест на целевом сервере.

Версионные дневные заказы и выкупы Sales Funnel добавлены миграцией 020; расписание накопления истории и read-модель обзора остаются следующими частями P0.4. Таблицы расширенной рекламы, запасов и контрольных точек добавляются следующими миграциями. Таблицы MVP не выдаются за завершённую реализацию всех функций концепции.
